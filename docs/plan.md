# 요약

가상 데이터로 규칙 기반 출동 스케줄링 agent와 하네스 기반 AI agent를 나란히 구현하고, 결과 분석 agent가 개선안을 내서 시뮬레이션으로 검증하는 6주 과제다. 핵심 메시지는 "AI가 규칙보다 낫다"가 아니라 "같은 모델도 하네스 설계에 따라 결과가 이만큼 달라진다"이다. 여기에 더해, 규칙이 명확한 반복 실행은 규칙 엔진이 싸고 빠르며, AI는 규칙을 분석·개선하는 시행착오에서 시간과 비용 우위가 있다는 역할 분담을 숫자로 보인다(상세: [AI 적용 경계](ai-application-boundary.md)).

| 단계 | 내용 | 핵심 산출물 | 대표 지표 |
|---|---|---|---|
| 1단계 | 규칙 agent(기준선) + AI agent를 하네스 L0~L5로 쌓아 비교, UI로 시각화 | 규칙 엔진, AI agent, domain-spec.md, 비교 UI | 하네스 레벨별 할당성공률, 필수조건 위반 0건 |
| 2단계 | 결과·트레이스를 분석해 실패 패턴과 원인 가설 도출 | 분석 agent, 분석 리포트 화면 | 심어둔 패턴 탐지율, 오탐 건수 |
| 3단계 | 규칙 파라미터·하네스 개선안 제안 → 시뮬레이션 → 사람 승인 | 개선 루프, 전후 비교 화면 | 개선 전후 할당성공률 변화 |
| 4단계 | 규칙 엔진이 남긴 미할당 건을 AI agent가 처리 | 확장 로드맵(이번 범위 밖) | — |

가상 데이터에 문제 패턴을 의도적으로 심어두어, 분석 agent의 성능을 정답과 대조해 정량 평가한다.

# 1. 배경 및 목적

실제 출동효율화(최적SM추천) Agent 기획서에는 AI가 들어갈 자리가 이미 열려 있다. ⑥번은 AI스케쥴링 결과를 지점·작업유형·시간대별 성공(근거)/실패(사유)로 적재해 튜닝 분석에 쓰는 것이고, ⑦번은 업무이력 스냅샷으로 대량 시뮬레이션을 돌려 할당성공률 전후를 비교하는 것이다. 기획서에는 "Ideation Agent 적용 가능"이라는 메모도 있다.

이 과제는 그 튜닝 분석·개선 구간을 AI agent로 채우는 방법을 검증한다. 기존 규칙 로직을 대체하는 것이 아니라, 규칙 로직을 다루고 개선하는 역할에 AI를 둔다.

**원안 대비 재정의한 점**

| 단계 | 원안 | 재정의 | 이유 |
|---|---|---|---|
| 1 | 출동최적화 agent를 AI로 복제 | 규칙 엔진은 코드로 구현, AI agent는 규칙 문서와 도구로 할당하며 하네스를 단계별로 적용 | LLM으로 규칙을 흉내 내면 일관성·필수조건 준수에서 불리. 하네스 효과를 보여주는 구조로 전환 |
| 2 | 결과 자체 분석 agent | 유지, 정답표 기반 평가 추가 | 가상 데이터라 탐지 성능을 정량 평가 가능 |
| 3 | 2단계 agent가 1단계 agent 고도화 | 규칙 파라미터 개선 + AI agent 하네스 개선, 시뮬레이션 검증 후 사람 승인 | 기획서 ⑦번 기능을 그대로 활용, 효과를 숫자로 제시 |
| 4 | 미할당 건을 AI agent가 할당 | 향후 과제로 방향만 제시 | 6주 범위 초과, 실제 로직 대체로 오해될 소지 |

**목적**

- 하네스 엔지니어링의 효과를 같은 데이터·같은 모델에서 정량적으로 보여준다
- 결과 분석과 개선 제안을 자동화해 운영 튜닝 공수를 줄일 수 있음을 검증한다
- 향후 업무가 agent로 전환될 때 효과를 검증하는 기반(시뮬레이터, 평가 방식, 정형화된 규칙 문서)을 만든다
- AI를 쓸 자리와 쓰지 않을 자리의 경계를 비용·시간 수치로 제시한다: 반복 실행은 규칙 엔진, 개선 설계는 AI ([AI 적용 경계](ai-application-boundary.md))

# 2. 과제 범위

구현 범위는 1~3단계이며, 4단계는 발표에서 향후 과제로 방향만 제시한다. 실제 시스템과 실제 데이터는 사용하지 않는다.

| 구분 | 포함 | 제외 |
|---|---|---|
| 데이터 | 가상 데이터 생성기(seed 고정) | 실제 지시서·작업자 데이터 |
| 동선 | 가상 격자 좌표 기반 거리·이동시간 계산 | TMAP API 연동 |
| 규칙 agent | 기획서 로직(가중치, 3단계 매칭, CEI 명장 우선, 동선) 코드 구현 | 실제 출동최적화 agent 연동 |
| AI agent | 하네스 L0~L5 단계별 구현 | 파인튜닝, 오픈웨이트 모델 서빙 |
| 분석·개선 | 분석 agent, 개선안 제안, 시뮬레이션 검증, 사람 승인 | 개선안 자동 반영 |
| 4단계 | 방향 제시(로드맵 슬라이드) | 구현 |

**원칙**

- 실제 프로젝트와 완전히 분리한다. 진행 중인 출동최적화 프로젝트 일정에 영향을 주지 않는다
- 필수 조건(기술 보유, 고위험 자격 등) 위반은 어떤 단계에서도 0건이 기준이다
- 모든 파라미터와 규칙은 파일(params.yaml, domain-spec.md)로 분리해 코드 수정 없이 바꿀 수 있게 한다

# 3. 가상 데이터 설계

지점 3개, 작업자 30명, 하루 지시서 150건, 10일치를 seed 고정으로 생성하고, 문제 패턴 4개를 의도적으로 심어 정답표로 쓴다.

**규모**

| 항목 | 규모 | 비고 |
|---|---|---|
| 지점 | 3개 (A·B·C) | 격자 지도 위 관할 구역 |
| 작업자 | 30명 | 지점별 약 10명 |
| 지시서 | 하루 150건 × 10일 | 개통·장애 혼합 |
| 지도 | 가상 격자 좌표 | 거리 × 평균 속도로 이동시간 계산 |

**스키마**

| 데이터 | 주요 필드 |
|---|---|
| 작업자 | ID, 소속 지점, 보유 기술(HFC/FTTx/CATV), 고위험·승주 자격, 관할지역, 가능시간, CEI 등급(명장 여부), 좌표 |
| 지시서 | ID, 작업유형(개통/장애), 매체, 난이도(승주/옥외/고위험), 건물유형(주택/아파트), 고객 희망시간, 좌표 |
| 할당 결과 | 지시서 ID, 작업자 ID, 매칭 단계, 이동시간, 성공/실패, 근거 또는 실패 사유 |

**심어둘 패턴 (정답표)**

| 패턴 | 심는 방법 | 예상 결과 |
|---|---|---|
| P1. 시간대 수요 집중 | B지점 오전 9~11시에 아파트 FTTx 지시서를 몰리게 생성 | 해당 시간대 3단계 매칭 실패 집중 |
| P2. 자격자 편중 | 승주 자격자를 A지점에 몰아 배치 | C지점 승주 작업 미할당 |
| P3. 가능시간 불일치 | 일부 작업자 가능시간을 희망시간 분포와 어긋나게 설정 | 가용 인력인데 활용률 낮음 |
| P4. 경계 지역 수요 | 지점 경계 지역에 고객 좌표를 몰리게 생성 | 지역 +1km 완화 시 성공률 급상승 |

정답표는 분석 agent에게 공개하지 않고 평가에만 쓴다.

# 4. 1단계: 규칙 agent와 하네스 기반 AI agent

같은 데이터를 규칙 agent와 AI agent에 넣어 비교하고, AI agent는 하네스 계층을 하나씩 켜며 매 레벨 성능을 측정한다.

## 4.1 규칙 agent (기준선)

기획서 로직을 파이썬 코드로 구현한다. 가중치, 매칭 단계 범위, CEI 기준값 등 모든 파라미터는 params.yaml에 둔다. 이 코드는 3단계의 시뮬레이터이자 AI agent의 제약 검증기 역할을 겸한다.

처리 흐름: 지시서 → 작업소요 가중치 → 시간·지역 3단계 매칭 → CEI 명장 우선 → 최적 동선 → 할당 결과·근거

기획서 ①~⑤번 순서를 그대로 따르며, 각 단계의 판단 근거를 결과에 기록한다.

## 4.2 AI agent 하네스 레벨

| 레벨 | 추가 계층 | 구현 내용 |
|---|---|---|
| L0 | 없음 | 지시서와 작업자 목록을 통째로 주고 배정 요청 |
| L1 | 컨텍스트 | domain-spec.md 주입 |
| L2 | 도구 | 후보 조회, 이동시간 계산, 작업자 일정 조회 도구 제공 |
| L3 | 검증 루프 | 배정안을 규칙 엔진 제약 검증기에 통과, 위반 시 사유를 돌려주고 재시도 |
| L4 | 가드레일 | 필수조건 위반 차단, 매칭 완화·명장 외 배정 등은 사람 승인 대기 |
| L5 | 관측성 | 판단·도구 호출·재시도를 트레이스로 기록 (2단계 입력) |

예상 결과는 L0에서 위반이 다수 발생하고, 레벨이 올라갈수록 규칙 agent 수준에 근접하며, L3 이후 위반 0건이다.

## 4.3 domain-spec.md (정형화된 규칙 문서)

다른 업무로 옮길 때 이 파일과 도구만 바꾸면 되도록 섹션을 고정한다.

| 섹션 | 내용 |
|---|---|
| 목적 | agent가 달성할 목표 |
| 필수 조건 | 반드시 지켜야 하는 제약 (기술, 자격) |
| 선호 조건 | 점수형 목표 (희망시간, 이동거리, 명장 우선) |
| 판단 순서 | 조건 적용 순서와 매칭 완화 단계 |
| 예외 처리 | 후보 없음, 동점, 승인 필요 기준 |
| 사용 도구 | 도구 목록과 사용 시점 |

# 5. 1단계 UI 설계

한 화면에 네 영역을 두고, 하네스 토글을 바꾸면 AI agent 결과가 다시 그려지는 구조로 하네스 효과를 눈으로 보여준다.

| 영역 | 보여주는 것 | 발표 활용 |
|---|---|---|
| 지도 뷰(좌우 분할) | 왼쪽 규칙 agent, 오른쪽 AI agent 배정 결과. 작업자·지시서 점, 동선 선, 미할당 빨간 점, 위반 경고 | 두 agent의 결과가 어디서 갈리는지 비교 |
| 하네스 컨트롤 패널 | L0~L5 토글과 실행 버튼 | L0 → L3에서 빨간 점이 사라지는 시연 |
| 트레이스 뷰 | 지시서 클릭 시 AI agent의 도구 호출, 후보 탈락 사유, 검증 반려와 재시도를 단계별 카드로 표시. 규칙 agent 판단을 옆에 병기 | AI 판단 과정이 블랙박스가 아님을 증명 |
| 지표 패널 | 할당성공률, 위반 건수, 평균 이동시간, 희망시간 일치율, 결과 일관성, 처리 시간·토큰 비용 | 장단점을 숫자로 솔직하게 제시 |

2단계와 3단계 화면(분석 리포트, 개선안 검증)은 같은 앱에 탭으로 추가한다.

**구현 원칙**

- 배포 없이 로컬에서 바로 띄울 수 있게 한다 (FastAPI + 단일 HTML 또는 React)
- 실시간 느낌은 폴링이나 SSE로 충분하다
- 발표용으로 결과를 미리 계산해 캐시하는 모드를 둔다 (라이브 실패 대비)

# 6. 2단계: 결과 분석 agent

분석 agent는 두 agent의 할당 결과와 L5 트레이스를 읽고, 실패 패턴과 원인 가설을 근거 데이터와 함께 제시한다.

**입력과 도구**

- 입력: 할당 결과(성공 근거·실패 사유), AI agent 트레이스 로그, 작업자·지시서 데이터
- 도구: 지점·시간대·작업유형·실패사유별 집계, 작업자 활용률 조회, 특정 조건 지시서 목록 조회

**출력 예시**

> B지점 9~11시 아파트 FTTx 지시서의 62%가 3단계 매칭에서 실패. 해당 시간대 FTTx 가능 인력 2명. (근거: 집계 결과 링크)

**환각 억제**: 수치는 반드시 집계 도구 결과를 인용하게 하고, 근거 없는 수치는 리포트에서 제외한다.

**평가**: 정답표(3장 P1~P4)와 대조해 탐지율과 오탐 건수를 잰다. 분석 agent는 정답표를 볼 수 없다.

**UI**: 분석 리포트 탭에 발견 패턴을 카드로 표시하고, 카드를 클릭하면 지도에서 해당 지시서들을 하이라이트한다.

# 7. 3단계: 개선 제안과 시뮬레이션 검증

분석 결과로 개선안을 제안하고, 시뮬레이션으로 효과를 확인한 뒤 사람이 승인해야 반영한다. 이 루프를 2~3회 돌린 기록이 발표의 개선 추이가 된다.

처리 흐름: 분석 리포트 → 개선안 제안 → 10일치 재시뮬레이션 → 전후 지표 비교 → 사람 승인 (승인 시 params.yaml·domain-spec.md 반영 / 반려 시 개선안 재작성)

**개선 대상 두 가지**

| 대상 | 예시 | 검증 방법 |
|---|---|---|
| 규칙 파라미터 (params.yaml) | B지점 오전만 지역 범위 +1km 완화 | 규칙 엔진으로 10일치 재실행, 할당성공률·이동시간·위반 건수 비교 (기획서 ⑦번 방식) |
| AI agent 하네스 (domain-spec.md, 도구 설명) | 반복 실패 유형에 대한 판단 규칙 추가 | AI agent 재실행, 동일 지표 비교 |

**UI**: 개선안 탭에 제안 카드마다 시뮬레이션 전후 수치와 승인/반려 버튼을 둔다. 반영 이력은 회차별로 남긴다.

# 8. 평가 지표

필수조건 위반은 0건이 절대 기준이고, 나머지는 점수형 지표로 추이를 본다. 목표 수치는 2주차에 확정한다.

| 단계 | 지표 | 기준·기대 결과 |
|---|---|---|
| 1단계 | 하네스 레벨별 할당성공률 | L5에서 규칙 agent 대비 격차 축소 |
| 1단계 | 필수조건 위반 건수 | L3 이후 0건 |
| 1단계 | 평균 이동시간, 희망시간 일치율 | 규칙 agent와 비교 |
| 1단계 | 결과 일관성(동일 입력 3회 실행 시 동일 비율) | AI agent의 약점으로 솔직하게 제시 |
| 1단계 | 건당 처리 시간, 건당 토큰 비용 | 규칙 agent($0) vs AI agent 레벨별. 품질 지표와 같은 표에 표시 |
| 2단계 | 심어둔 패턴 탐지율 | 예: 4개 중 3개 이상 |
| 2단계 | 오탐 건수 | 0건 목표 |
| 3단계 | 개선 적용 전후 할당성공률 | +X%p (시뮬레이션 기준) |
| 3단계 | 개선 1회전 비용·시간 (분석·제안 LLM 비용 + 시뮬레이션 시간) | 같은 분석을 사람이 할 때의 추정 소요 시간과 비교 |
| 3단계 | 제안 채택률 | 제안 중 시뮬레이션 효과가 확인된 비율 |

# 9. 시스템 구성

모든 구성요소는 로컬에서 동작하며, 외부 의존은 상용 LLM API 하나뿐이다.

데이터 흐름: 데이터 생성기 → 가상 데이터 → 규칙 agent(params.yaml) / AI agent(domain-spec.md, 규칙 agent에 검증 요청) → 결과·트레이스 → 분석 agent → 개선 제안 → 규칙 agent로 시뮬레이션. 결과·트레이스는 대시보드 UI로 표시.

| 구성요소 | 기술 | 비고 |
|---|---|---|
| 데이터 생성기 | Python | seed 고정, 패턴 주입 옵션 |
| 규칙 agent·시뮬레이터 | Python | params.yaml 로드, 검증기 API 제공 |
| AI agent·분석 agent | 상용 LLM API (Claude 등) + tool use | 하네스 레벨을 설정으로 전환 |
| 결과 저장 | JSON 또는 SQLite | 회차별 결과·트레이스 보관 |
| 백엔드 | FastAPI | 실행·조회 API |
| 프런트엔드 | 단일 HTML 또는 React | 격자 지도, 토글, 트레이스, 지표 |

# 10. 교육 관점 ① 기술적 성취도

이 과제로 익히는 기술은 "에이전트를 만드는 기술"보다 "에이전트를 믿을 수 있게 만들고 숫자로 증명하는 기술"이며, 각 역량마다 발표에서 보여줄 성취 증거를 짝지어 둔다.

**단계별 기술 역량과 성취 증거**

| 단계 | 익히는 기술 | 성취 증거 |
|---|---|---|
| 준비 | 도메인 규칙의 명세화 (필수 조건과 선호 조건 분리, 판단 순서 정의) | params.yaml, domain-spec.md |
| 준비 | 합성 데이터 설계와 결함 주입 (정답이 있는 테스트 환경 구축) | 데이터 생성기, 정답표 |
| 1단계 복제 | 규칙 로직의 결정적 구현과 설정 분리 | 규칙 agent, 파라미터만 바꿔 재실행되는 시뮬레이터 |
| 1단계 복제 | LLM tool use 설계 (도구 스키마, 도구 설명 작성) | AI agent 도구 목록과 호출 트레이스 |
| 1단계 복제 | 하네스 5계층 구현 (컨텍스트, 도구, 검증 루프, 가드레일, 관측성) | L0~L5 레벨별 지표 추이 |
| 1단계 비교 | 동일 조건 비교 실험 설계 (고정 seed, 반복 실행, 일관성 측정) | 규칙 vs AI 지표 비교표 |
| 2단계 분석 | 트레이스 기반 실패 분석, 근거 인용 강제로 환각 억제 | 분석 리포트, 탐지율·오탐 수치 |
| 3단계 개선 | 제안 → 시뮬레이션 → 승인의 휴먼 인 더 루프 설계 | 회차별 개선 이력, 전후 비교 |
| 전 단계 | 관측성 UI 구현 | 대시보드 시연 |

**성취 수준 기준**

| 수준 | 기준 |
|---|---|
| 기본 | 규칙 agent와 AI agent(L3 이상)가 동작하고, 위반 0건과 비교 지표를 제시 |
| 목표 | L0~L5 추이, 패턴 탐지율, 개선 루프 2회 이상 결과를 UI로 시연 |
| 도전 | 11장의 범용 구조로 두 번째 최적화 주제에 적용해 동작 확인 |

기술적 성취를 발표에서 보일 때는 기능 목록이 아니라 "하네스 레벨이 올라갈 때 위반이 0이 되었다", "심어둔 문제 4개 중 N개를 찾았다"처럼 측정 결과로 제시한다.

# 11. 교육 관점 ② 범용 구조

복제 → 비교 → 분석 → 개선의 흐름을 도메인과 무관한 **공통 코어**로 만들고, 출동 스케줄링 관련 부분은 교체 가능한 **도메인 팩**으로 분리한다. 다른 최적화 주제에 적용할 때는 도메인 팩만 새로 만든다.

- 공통 코어(재사용): 하네스 러너(L0~L5 전환), 평가 러너(반복 실행·지표), 분석 agent 골격, 개선 루프(제안·시뮬·승인), UI 셸
- 도메인 팩(교체): 데이터 생성기·결함 주입, 규칙 엔진(solve·validate), domain-spec.md·params.yaml, 도구·지표·시각화 어댑터

## 11.1 공통 코어와 도메인 팩의 경계

| 구분 | 공통 코어 (한 번 만들고 재사용) | 도메인 팩 (주제마다 새로 작성) |
|---|---|---|
| 복제 | 하네스 러너, 검증 루프, 가드레일, 트레이스 로거 | 규칙 엔진, 도구 정의, domain-spec.md |
| 비교 | 평가 러너 (고정 seed, 반복 실행, 일관성 측정, 비교표 생성) | 도메인 지표 정의 (예: 할당성공률, 이동시간) |
| 분석 | 분석 agent 골격, 범용 집계 도구 (차원별 실패 집계) | 분석 차원 선언 (예: 지점, 시간대, 작업유형), 실패 사유 코드 |
| 개선 | 제안 → 시뮬레이션 → 승인 → 반영 루프, 개선 이력 | 조정 가능한 파라미터 목록과 허용 범위 |
| 데이터 | 결함 주입과 정답표 기반 탐지율 채점기 | 데이터 스키마, 생성기, 심을 패턴 |
| UI | 비교 뷰 틀, 하네스 토글, 트레이스·지표·분석·개선 탭 | 결과 시각화 어댑터 (지도, 간트 차트, 표 등) |

## 11.2 도메인 팩 인터페이스 (계약)

도메인 팩은 아래 함수와 파일만 제공하면 코어에 연결된다.

| 항목 | 역할 |
|---|---|
| generate(seed, faults) | 가상 데이터와 정답표 생성 |
| solve(instance, params) | 규칙 기반 해답 생성 (기준선, 시뮬레이터) |
| validate(instance, decision) | 필수조건 위반 목록 반환 (AI agent 검증 루프에 사용) |
| metrics(result) | 도메인 지표 계산 |
| tools() | AI agent에 제공할 도구 목록 |
| domain-spec.md | 목적, 필수 조건, 선호 조건, 판단 순서, 예외 처리, 사용 도구 (고정 섹션) |
| params.yaml | 규칙 파라미터와 조정 허용 범위 |
| dimensions | 분석 agent가 집계할 차원과 실패 사유 코드 |

**표준 결과 레코드**: 항목 ID, 결정, 성공/실패, 사유 코드, 근거, 도메인 지표 값. **표준 트레이스 레코드**: 단계, 유형(도구 호출·검증·재시도·승인), 입력, 출력, 시각. 두 형식을 고정해야 분석 agent와 UI가 도메인과 무관하게 동작한다.

## 11.3 다른 최적화 주제 적용 예

| 주제 | 규칙 엔진 (solve) | 필수 조건 (validate) | 분석 차원 | 시각화 |
|---|---|---|---|---|
| 출동 스케줄링 (이번 과제) | 가중치·3단계 매칭·동선 | 기술 보유, 고위험 자격 | 지점, 시간대, 작업유형 | 지도 |
| 교대 근무표 편성 | 순번·선호 반영 배정 | 연속 근무 제한, 최소 인원 | 부서, 요일, 근무조 | 간트 차트 |
| 자재 재고 배분 | 우선순위 기반 배분 | 재고 한도, 최소 보유량 | 창고, 품목, 기간 | 표·막대 |
| 설비 점검 일정 | 주기·위험도 기반 배정 | 점검 주기 초과 금지 | 설비 유형, 지역, 월 | 캘린더 |

## 11.4 범용화 원칙

- 처음부터 범용으로 만들지 않는다. 출동 스케줄링으로 먼저 완성하고, 두 번째 주제에 적용할 때 실제로 바꿔야 했던 부분만 인터페이스로 뽑는다
- 범용성 검증은 두 번째 도메인 팩으로 한다. 5~6주차에 여유가 있으면 교대 근무표 같은 작은 주제로 최소 도메인 팩을 만들어 코어 수정 없이 돌아가는지 확인한다 (10장의 도전 수준)
- 코어를 수정해야 했다면 그 지점을 기록해 발표의 "범용화 교훈"으로 쓴다
- 산출물로 도메인 팩 작성 가이드(domain-spec.md 템플릿, 결함 주입 패턴 카탈로그, 인터페이스 설명)를 남긴다

# 12. 6주 일정 및 역할 분담

분석설계 2주, 구현 3주, 발표 준비 1주로 진행하며, 3주차부터 한 명은 agent, 한 명은 UI를 병행한다.

| 주차 | 담당 A (데이터·agent) | 담당 B (UI·평가) | 산출물 |
|---|---|---|---|
| 1주 | 가상 데이터 스펙, 심을 패턴 4개, params.yaml 파라미터 목록 | domain-spec.md 템플릿, 평가 지표·정답표 | 데이터·규칙 스펙 |
| 2주 | 하네스 L0~L5 정의, 도구 목록 | UI 와이어프레임, 발표 장면 대본 | 설계서, 스토리보드 |
| 3주 | 데이터 생성기, 규칙 agent | 지도 뷰, 지표 패널 | 규칙 agent 동작 화면 |
| 4주 | AI agent L0~L5, 트레이스 로깅 | 하네스 토글, 트레이스 뷰 연결 | 1단계 완성 |
| 5주 | 분석 agent, 개선 루프 2~3회 | 분석 리포트·개선안 탭 | 2~3단계 결과 기록 |
| 6주 | 지표 정리, 리허설 | 시연 녹화 백업, 발표 자료 | 발표 |

**일정이 밀릴 때 줄이는 순서**

1. 3단계의 AI agent 하네스 개선 (규칙 파라미터 개선만 유지)
2. L4 가드레일의 승인 UI (차단 로직만 유지)
3. 트레이스 뷰의 규칙 agent 병기

하네스 토글 시연, 패턴 탐지율, 파라미터 개선 전후 수치 세 가지만 있어도 발표는 성립한다. 발표 이틀 전부터는 기능 추가를 멈춘다.

# 15. 확장 로드맵

4단계는 이번 과제에서 구현하지 않고, 발표에서 향후 과제로 방향만 제시한다.

**4단계 방향: 규칙 엔진과 AI agent의 역할 분담**

할당 전체를 AI로 대체하지 않는다. 규칙 엔진이 먼저 처리하고, 전일자 미할당 지시서(개통·장애) 중 규칙 엔진이 처리하지 못한 잔여 건만 AI agent가 대안을 찾아 추천한다. AI의 추천안도 규칙 엔진 검증기를 통과해야 하며, 필수조건 위반 0건 기준은 동일하다. 이번 과제의 L3(검증 루프)와 L4(가드레일) 구조가 그대로 기반이 된다.

| 확장 방향 | 내용 |
|---|---|
| 4단계 미할당 처리 agent | 규칙 엔진 잔여 건에 대한 AI 추천, 사람 승인 후 할당 |
| 실제 데이터 적용 | 업무이력 스냅샷으로 가상 데이터 대체, 기획서 ⑦번 시뮬레이션과 연계 |

| 정식 평가 도구 도입 | 자체 평가 러너를 promptfoo 등 정식 도구로 전환 |

**도메인 팩 확장 경로 (M6 이후)**

도메인 탭(M6-a)으로 규칙과 데이터를 보이게 한 다음, 같은 틀을 새 업무에 적용하는 순서다. 앞 단계에서 확인한 공통점만 다음 단계에서 일반화한다(구현 원칙: 과도하게 일반화하지 않는다).

| 단계 | 내용 | 판단 기준 |
|---|---|---|
| M6-b 사람이 만든 개선안 | 도메인 탭에서 값을 고치면 개선안으로 만들어 기존 허용 범위 검사·시뮬레이션·승인 흐름을 탄다 | 새 경로 없이 기존 파이프라인 재사용 |
| 두 번째 도메인 팩 (AI 보조 제작) | 도메인 설명을 주면 코딩 agent가 팩을 작성하고, 계약 테스트·결함 드러남 테스트·모범 분석가 테스트가 합격 기준이 된다 | 두 도메인의 공통점과 차이를 실제로 확인 |
| 팩 생성 마법사 | 선언 파일 4종은 화면에서 작성, 코드 부분(생성기·규칙 엔진·도구·지표)은 AI 생성 + 사람 검토 후 커밋해야 등록 | 생성 코드는 사람이 검토하기 전에 실행하지 않는다 |
| 실데이터 로더 | `generate(seed, faults)` 옆에 `load(source)` 추가. 정답표가 없으므로 평가는 탐지율 대신 사람 판정과 개선 전후 비교 중심 | 실제 업무 적용의 관문 |

**M6-b 상세 계획: 사람이 만든 개선안 (보류 중, 아래 결정 후 착수)**

목표: 도메인 탭에서 사람이 규칙 파라미터를 고치되, 파일을 바로 바꾸지 않고 AI 개선안과 같은 흐름(허용 범위 검사 → 시뮬레이션 → 사람 승인 → params.yaml 반영 → 이력)을 타게 한다. 새 반영 경로를 만들지 않아 "변경은 검사·시뮬레이션·승인을 거친다"는 원칙이 유지된다.

현재 구조에서 걸리는 점: 개선안(proposals)은 분석 리포트와 AI 개선안 묶음(batch)에 반드시 연결된다(report_id·batch_id NOT NULL). 시뮬레이션은 리포트가 가리키는 실행의 데이터와 발견 구간을 쓰고, 이력은 리포트·묶음에서 AI 비용·시간을 가져온다. 도메인 탭에서 바로 고치는 경우에는 리포트가 없다.

| 구분 | 내용 |
|---|---|
| 백엔드 | `POST /proposals/manual` (기준 실행, params_changes, override_rules, 사유). 검증은 기존 `params_errors` 재사용(허용 범위, bounds·docs 메타 키 차단). 개선안에 작성자(`ai`/`human`)와 기준 실행 저장. 시뮬레이션·승인·반려·stale 처리는 기존 코드 재사용. 리포트가 없으면 발견 구간 대신 사람이 고른 구간(예: area_zone=boundary)의 실패율, 없으면 전체 지표. 이력에 작성자 표시 |
| 화면 | 도메인 탭 규칙 파라미터에 "수정안 만들기": 값 편집(허용 범위 즉시 검사, 고정값·설명은 편집 불가), 구간 조건 편집기(차원·값 선택 → 파라미터·값), 사유 필수, 제출 전 현재→제안 차이 미리보기. 제출하면 개선 탭에 "사람 작성" 배지로 나타나 기존처럼 시뮬레이션 → 승인 |
| 테스트 | 사람 개선안 생성, 범위 밖·메타 키 거부, 시뮬레이션 → 승인 → params.yaml 버전 증가, 이력 작성자, 시연 모드에서 작업 복사본에만 반영 |
| 문서 | 화면 매뉴얼 "수정안 만들기" 절, ai-application-boundary.md에 사람 개선과 AI 개선 비교 관점 |
| 범위 밖 | 명세 편집(결정 2), 동시 편집·권한 관리, git 커밋 자동화(승인 후 커밋은 계속 사람이) |

착수 전 결정할 것:

| # | 결정 | 선택지 | 추천 |
|---|---|---|---|
| 1 | 저장 방식 | (a) proposals의 report_id·batch_id를 비울 수 있게 하고 author·run_id 열 추가. SQLite는 제약 변경 시 테이블 재생성 마이그레이션 필요, 스키마 변경이라 사전 합의 대상 / (b) 사람용 빈 리포트·묶음을 만들어 기존 구조에 끼움. 스키마는 그대로지만 분석 재생·리포트 목록 등 여러 곳에 걸러내는 예외 처리가 생김 | (a) 데이터 모델이 정직하고 예외 처리가 적음 |
| 2 | 명세도 사람이 편집 | 파라미터만 / 명세 섹션 편집 포함 | 파라미터만. 명세 시뮬레이션은 AI 실행 비용이 들어 실제 API 실험 뒤에 다룬다 |
| 3 | 시뮬레이션 기준 데이터 | 현재 데이터셋 전체 규칙 실행(없으면 자동 실행) / 사용자가 실행 선택 | 현재 데이터셋 전체 규칙 실행. 비용 없음, 분석 탭과 같은 기준 |
| 4 | 편집 위치 | 도메인 탭 안 / 개선 탭 "직접 작성" 폼 | 도메인 탭. 값·설명·허용 범위를 보며 고치고 결과는 개선 탭으로 모인다 |

**M7 상세 계획: 하네스 가시화**

하네스 레벨(L0~L5)은 지금 화면에서 레벨 버튼과 플래그 ✓/– 표시로만 보인다. 플래그가 AI에게 무엇을 바꾸는지, 레벨에 따라 결과가 어떻게 달라지는지를 화면에서 설명하고 보여주는 것이 목표다. 이번 범위는 M7-a(파이프라인 그림)만 구현하고, 나머지는 실제 API 실험 전후로 나눠 진행한다.

| 항목 | 내용 | 상태 |
|---|---|---|
| C. 하네스 파이프라인 그림 | 선택한 레벨의 처리 흐름을 단계 그림으로 보여준다 (아래 상세) | M7-a 완료 |
| A. 레벨 추이 차트 | x축 L0~L5, y축 할당성공률·위반 건수·건당 비용. 반복 실행은 최소~최대 범위, 규칙 agent는 기준선. 발표 13장 "하네스 레벨별 추이 그래프"에 해당 | M7-b 후속 (실제 API 실험 직전) |
| B. 하네스 효과 집계 | 레벨별 재시도 발생·재시도로 통과·차단·승인 대기 건수, LLM 호출 수. 결정 기록의 retries·status로 계산 | M7-b 후속 |
| D. AI 입력 미리보기 | 레벨과 항목을 고르면 실제로 보내는 시스템 프롬프트·도구 목록·첫 메시지를 LLM 호출 없이 보여줌. L0·L1은 인스턴스 JSON 크기(토큰 추정) 표시 | M7-b 후속 |
| E. 두 레벨 지도 나란히 비교 | 비교 탭의 규칙 agent 자리에 다른 AI 레벨 | 검토 대상 |
| F. 사용자 정의 레벨 | 화면에서 플래그 조합 | 하지 않음. 레벨은 harness_levels.yaml로만 정의한다 |

M7-a 파이프라인 그림 상세:

| 구분 | 내용 |
|---|---|
| 위치 | 비교 탭 하네스 줄의 "하네스 설명" 펼침. 펼치면 레벨 버튼 아래에 그림 패널이 열리고, 레벨 버튼을 바꾸면 그림도 바뀐다 |
| 단계 | ① 입력: 기본 지시(항상) + 도메인 명세(spec) + 데이터 제공 방식(인스턴스 전체 JSON 또는 조회 도구 N개) → ② LLM 호출(항목당 최대 호출 수) → ③ 결정 제출(submit_decision, 모든 레벨 공통) → ④ 검증(validate, 위반이면 사유를 돌려주고 ②로 재시도, 최대 N회) → ⑤ 가드레일(확정 / 차단 / 승인 대기) → ⑥ 기록(최종 결과만 / 모든 단계). 별도 표시: 사후 채점(모든 레벨에서 validate로 위반을 셈) |
| 켜짐·꺼짐 | 꺼진 단계는 흐리게 하고 "L3부터"처럼 켜지는 레벨을 표시. 데이터 제공 방식은 켜고 끄는 것이 아니라 바뀌는 것(L0·L1 인스턴스 전체 → L2부터 도구)이라 두 상태를 모두 보여주고 현재 쪽을 강조 |
| 단계 설명 | 단계를 누르면 아래에 설명: 무엇을 하는지, 설정 위치(harness_levels.yaml·llm.yaml·domain-spec.md·params.yaml), 결과에서 어디에 드러나는지(예: 가드레일 → 비교 지도의 ◯ 승인 대기·✕ 차단, 트레이스는 L5만) |
| 레벨 매트릭스 | 그림 아래 L0~L5 × 단계 표(●/○). 현재 레벨 행 강조, 행을 누르면 레벨 전환 |
| 도메인 무관 | 단계 구조와 설명은 코어 개념이라 공통. 도메인별 내용(도구 이름·설명, 승인 필요 조건, 필수조건 수)은 도메인 정의 API에서 가져온다 |
| API (필드 추가만) | `GET /harness/levels`의 llm 정보에 max_llm_calls_per_item 추가. `GET /domains/{domain}/definition`에 tools(도구 이름·설명) 추가: 도메인 기본 인스턴스(seed 0, 결함 없음)로 tools()를 불러 handler를 뺀 목록 |
| 그리기 | HTML·CSS 상자와 화살표(재시도는 되돌아가는 화살표). 색은 기존 토큰, 어두운 테마 대응. 좁은 화면에서는 세로 배치 |
| 테스트·확인 | API 필드 테스트(도구 목록에 handler가 없는지 포함), tsc·빌드, Playwright로 L0·L2·L3·L5 캡처 확인 |
| 문서 | 화면 매뉴얼 "하네스 레벨" 절에 그림 캡처와 설명, README 하네스 레벨 표에 "단계 그림은 비교 탭 하네스 설명" 안내 |
| 범위 밖 | A·B·D·E (M7-b 이후), 레벨 추가·수정 |

**M8 상세 계획: 화면 쉽게 보기 (용어 정리 + 요약 먼저, 상세는 펼쳐서)**

화면이 한 번에 너무 많은 정보를 보여줘 사용자가 혼란스럽다. 정보는 하나도 지우지 않고 (1) 화면 용어를 쉬운 말로 바꾸고, (2) 판단에 필요한 결론만 먼저 보여주고 근거·원자료는 "상세보기"로 펼치게 한다. 용어를 먼저 바꾸는 이유는 요약 문장이 바뀐 용어로 쓰이기 때문이다.

원칙:

| 구분 | 내용 |
|---|---|
| 바꾸는 곳 | **화면에 보이는 글자만.** 코드 이름, API, 설정 파일, 코어 계약(`core/interfaces.py`)은 그대로다 (코어 재사용 레포에 영향 없음) |
| 원래 용어 | 화면은 쉬운 말만. 원래 용어는 마우스 올림 설명과 상세보기에만 남긴다 |
| 한 곳에서 관리 | `web/src/terms.ts`에 용어를 모으고 모든 화면이 여기서 가져온다. 같은 목록을 화면 매뉴얼의 "용어표"로 쓴다 |
| 업무 용어 유지 | 지시서, 작업자, 지점, 승인, 반려처럼 현업이 쓰는 말은 바꾸지 않는다 |
| 기술 표기 | 파일 경로, 설정 키, 함수 이름(`validate()` 등), JSON 원문, 영문 사유 코드(`CAPACITY`)는 상세보기에만 |
| 하네스 레벨 | 이름 "하네스 레벨"과 L0~L5 표기는 유지한다(레벨 0~5 표기는 자율주행 단계 등으로 익숙하지만, 각 단계의 뜻은 이 프로젝트가 정한 것이라 이름만 보고는 알 수 없다). 버튼에 짧은 이름을 붙인다 |
| 위반은 숨기지 않음 | 규칙 위반이 1건이라도 있으면 요약에 빨간 숫자로 항상 보인다 |
| 숨은 양 표시 | 접힌 상세보기에는 "상세보기 (지표 7개 더)"처럼 숨은 내용의 양을 적는다 |
| 개발 문서 | plan.md, handoff.md, domain-pack-guide.md는 개발 용어를 유지한다(용어표로 연결) |

탭 이름: 도메인 → **규칙·데이터**, 비교 → **비교**, 트레이스 → **결정 과정**, 분석 → **문제 찾기**, 개선 → **개선 제안**

하네스 레벨 버튼: `L0 기본` · `L1 +규칙 문서` · `L2 +조회 기능` · `L3 +자동 검사` · `L4 +위험 결정 막기` · `L5 +과정 기록`

M8-a 구현 메모: 레벨 버튼의 짧은 이름은 `terms.ts`의 `levelShortName()`이 설정 파일 플래그에서 만든다(바로 앞 레벨보다 새로 켜진 기능, 레벨 이름에 고정하지 않음). 도메인 어댑터에 선택 필드 `MetricSpec.tech`, `reasonNames`, `DomainData.fieldLabels`, `ResultViewProps.reasonDetails`를 추가했다(모두 추가만). 서버·코어가 내는 문장(코어 사유 설명, 개선안 검사 오류, AI 응답, 업무 파일 내용)은 데이터라 그대로 둔다.

M8-b 구현 메모: `components/Details.tsx`(브라우저 기본 `<details>`, 접혀 있으면 내용을 그리지 않음)와 헤더의 "모두 펼치기"(localStorage `oah.expandAll`). 도메인 어댑터에 선택 필드 `MetricSpec.primary`(요약에 보일 핵심 지표), `MetricSpec.better`("up"/"down", 개선 제안 요약의 "나빠진 지표" 판정)를 추가했다(추가만, 없으면 요약에 규칙 위반·비용만 나온다). 규칙 위반·건당 비용은 모든 도메인 공통이라 어댑터 설정 없이 요약에 나온다. 비교 탭: 핵심 카드 3개 + 상세보기, 요약 비교표 + 상세보기(전체 열), 두 방식 실행 후 결론 한 줄. 개선 제안 탭: 상단 카드 → 한 줄, 제안 카드는 제목·요약 한 줄·버튼만 보이고 근거·바꿀 내용·전·후 표는 상세보기. 오류(적용 불가 이유, 미리 돌려보기 실패)는 접지 않는다.

M8-c 구현 메모: 문제 찾기는 결론 한 줄(심어둔 문제 N개 중 M개 찾음, 문제별 ✓/✕, 사람 확인 대기)과 찾은 문제 제목·조건 칩을 먼저, 수치 카드·설명·근거 데이터는 상세보기. 결정 과정은 결론 카드(최종 상태, 규칙 방식과 같은 결정인지, 다시 시도·자동 검사 걸림 횟수)와 단계 흐름 한 줄을 먼저, 단계별 카드는 상세보기. 상단은 시연 배너를 한 줄로, 심어둔 문제 체크박스와 반복·모델 설정은 펼치는 칩으로 접었다. 도메인 어댑터 선택 필드 `valueNames`(조건 값 → 화면 이름, 예: boundary → 경계 지역)와 `decisionText`(결정 한 줄 요약)를 추가했다(추가만). 결정 과정 탭에 남아 있던 dispatch 전용 표시("(n단계)")를 `decisionText`로 옮겨 공통 화면에서 도메인 필드를 직접 읽지 않게 했다.

주의: 시연 녹화 스크립트(`scripts/record_demo.mjs`)는 화면 글자(탭·버튼 이름)로 요소를 찾는다. 그래서 화면 글자나 구조를 바꾸는 단계마다 같은 PR에서 스크립트를 고치고, 끝까지 도는지 확인한 뒤 올린다. 단계 사이에 녹화가 깨진 상태로 main에 들어가지 않게 하기 위해서다.

**M9 Agent workflow (LangGraph) (완료)**

화면에서 탭을 오가며 하나씩 누르던 단계를 LangGraph `StateGraph` 하나로 묶어, 흐름이 한 단계(에이전트)씩 넘어가는 모습을 보여주는 탭(**Agent workflow (Langgraph version)**)을 추가했다. 각 레포(optimization-agent-workflow, optimization-agent-graph)가 완성된 모습이라면, 이 탭은 이 레포 안에서 **흐름 중심으로 간단히** 보여주고 **LangGraph 구조라 에이전트를 추가·확장할 수 있다**는 것을 보여주는 데 목적이 있다. 상세: [docs/workflow.md](workflow.md).

| 구분 | 내용 |
|---|---|
| 그래프 | 데이터 생성 → 규칙 방식 실행 → AI 방식 실행 → 결과 비교 → 규칙 방식 전체 실행 → AI 분석 → 개선 제안 → 미리 돌려보기 ◇ → 사람 승인 ◇ → 반영. ◇는 조건부 연결(좋아지지 않거나 반려하면 다음 제안) |
| 진행 | 모든 노드 앞에서 멈추고(`interrupt_before`) 사람이 [다음 실행]. 사람 승인은 노드 안 `interrupt()`로 멈추고 [승인]/[반려]를 받는다. 자동 진행은 두지 않았다(사용자 결정) |
| 연결층 | 노드는 기존 API를 같은 프로세스 안에서 부른다. 코어·API 로직 변경 없음, 시연 모드 그대로 동작. 도메인 지식은 화면이 넘겨주는 어댑터 지표 정의(`primary`, `better`)뿐 |
| 그림 | 서버가 컴파일한 그래프의 `get_graph()`로만 그린다 (노드를 추가하면 그림에도 바로 나온다) |
| 다른 탭과 연결 | 노드의 [탭에서 보기]가 같은 데이터·실행·분석·제안을 해당 탭에 넘긴다 |
| 의존성 | `pip install -e ".[workflow]"` (langgraph, httpx). 없으면 탭에 설치 안내만, 다른 탭은 그대로. CI는 설치해서 테스트 |
| API (추가) | `GET /workflow/graph`, `POST /workflow/runs`, `GET /workflow/runs/{id}`, `POST /workflow/runs/{id}/step` |
| 범위 밖 | 시연 녹화 장면(사용자 결정으로 추가 안 함), 여러 레벨 병렬 실행·여러 바퀴 개선(확장 예로 문서에만) |

**M10 LangGraph agents (완료)**

M9가 기존 에이전트를 노드로 감싸 연결만 했다면, M10은 **에이전트 내부까지 LangGraph로** 만든 별도 탭(**LangGraph agents**)이다. 기존 탭·코어는 그대로다.

| 구분 | 내용 |
|---|---|
| 상위 그래프 | 데이터 준비 → [배정 에이전트] → 평가 → 규칙 방식 전체 실행 → [분석 에이전트] → [개선 제안 에이전트] → 미리 돌려보기 ◇ → 사람 승인(interrupt) ◇ → 반영. 에이전트 단위로 멈추고 사람이 [다음 실행] |
| 배정 에이전트 | 다음 지시서 → AI 응답 ⇄ 조회 도구 → 결정 읽기 → 자동 검사 ◇ 다시 시도 → 위험 결정 막기 → 기록 → 과정 저장. **하네스 레벨 플래그가 노드·연결을 정한다** (L0: 도구·검사 없음 … L5: 전부) |
| 분석·개선 제안 에이전트 | 공통 하위 그래프(`build_tool_agent`): AI 응답 ⇄ 도구 → 검사 ◇ 반려 → 고쳐 오기. 분석은 근거 검사(돌려보냄), 개선 제안은 바꿀 수 있는 범위 검사(적용 불가로 표시) |
| 재사용 | 프롬프트·도구·검증·가드레일·집계·시뮬레이션·승인 반영은 코어 함수 그대로. 업무 규칙 문서 제안의 미리 돌려보기는 배정 에이전트 하위 그래프를 전·후로 다시 실행 |
| AI | 기존 LLM 클라이언트. claude(실제 API, 비용) / fake(리허설 가짜 AI, 조회 도구를 한 번 쓰도록 감쌈). 시연 모드는 항상 fake |
| 내부 진행 | 노드가 내는 기록(에이전트·노드·한 줄)을 화면이 실시간으로 받는다. 가짜 AI는 너무 빨라 내부 단계 사이에 간격(pace, 기본 0.2초) |
| 결과 | 탭 안에서만 (DB에 저장하지 않음). 승인 반영만 규칙 파일에 |
| API (추가) | `GET /agents/graph?level=`, `POST /agents/runs`, `GET /agents/runs/{id}?after=`, `POST /agents/runs/{id}/step` |
| 단계 | M10-a 백엔드·테스트, M10-b 화면·문서 (사용자 결정으로 2단계) |
| 화면 (M10-b) | 왼쪽 상위 그래프(단계별 결과 한 줄), 오른쪽 고른 에이전트의 내부 그래프(지금 노드 강조, 노드별 지나간 횟수, 실시간 진행 기록). 레벨을 바꾸면 배정 에이전트 그림이 바로 바뀐다. AI(가짜/Claude)·속도 선택. 상세: [docs/langgraph-agents.md](langgraph-agents.md) |

**M11 LangGraph agents 가로 그래프 (완료)**

목록처럼 보이던 세로 카드 대신, 갈래(조건부 연결)와 고리(되돌아감)가 선으로 보이는 가로 그래프로 바꿨다. 화면만 바뀌고 백엔드·API는 그대로다.

| 구분 | 내용 |
|---|---|
| 그리기 | React Flow(`@xyflow/react`) + dagre 자동 배치(왼쪽→오른쪽). 서버의 노드 순서(흐름 순서)로 앞으로 가는 연결만 배치에 쓰고 되돌아가는 연결은 노드 아래로 도는 곡선, 자기 자신 연결은 노드 위 고리 |
| 배치 | 위 = 상위 그래프 (넓어서 최소 배율을 두고 실행 중인 노드로 화면이 따라감), 가운데 = 고른 에이전트의 내부 그래프, 아래 = 단계 결과·진행 기록 (사용자 결정: 위아래 두 줄) |
| 실행 중 표시 | 지금 노드 강조, 노드별 지나간 횟수, 방금 지나간 연결은 움직이는 선 (연속한 두 진행 기록으로 계산) |
| 크기 | 그래프 탭 두 개는 탭을 열 때 불러온다 (첫 화면 번들은 그대로, 그래프 탭 +77KB gzip) |
| 범위 | LangGraph agents 탭만 (사용자 결정). Agent workflow 탭은 그대로 |

**M12 상세 계획: 분석·개선 고도화 — 코어 확장·장기 기억(이 레포)과 현장 의견 대화(별도 레포) (M12-a·M12-b·M12-c·M12-d 완료, 실제 API 실험은 실험 보고서 6.7~6.11절)**

목표: 실제 API 실험에서 드러난 분석·개선 단계의 약점을 두 방향으로 보완한다.

- **관점별 분석 에이전트**: 분석 에이전트 하나가 넓게 훑던 것을 관점별로 나눠 깊게 보게 한다.
- **현장 의견 반영**: 도메인 전문가·현장 업무자가 대화로 판단 기준(제약, 사실, 발견 판정)을 구체화하고, 그 결과가 구조화되어 개선 단계에 들어가게 한다.
- **회차 간 장기 기억**: 사람이 내린 판단(반려 사유, 발견 판정, 확인된 제약)이 다음 회차 에이전트 입력으로 돌아가게 한다.

원칙은 그대로다. AI는 찾고 제안하고, 코드는 확인하고, 사람은 고른다. 대화로 규칙이 바로 바뀌지 않고, 반영은 기존 검사 → 시뮬레이션 → 승인 흐름을 탄다.

*M12-a 채점기 보강 + 제약 지원 (이 레포)*

*M12-c 회차 간 장기 기억 (이 레포)*

배경: 지금 분석·개선 에이전트는 매 회차 처음 보는 사람처럼 시작한다. 사람이 내린 판단은 DB에 남지만 다음 회차 입력으로 돌아가지 않는다. 그래서 다음과 같은 일이 생길 수 있다.

- 반려한 개선안(예: 실험 3의 지점 간 협업 명세안)을 다음 회차에 같은 이유로 또 제안한다. 반려 사유는 저장되지만 개선 에이전트에게 주지 않는다. `propose(feedback=...)` 입력 경로는 있으나 회차를 넘어 연결돼 있지 않다.
- 사람이 오탐으로 판정한 발견을 분석 에이전트가 다시 올린다.
- 현장 제약("5km 불가")을 매 회차 다시 말해야 한다.

이 문제는 코딩 에이전트 세션을 운영할 때와 같은 구조다. 대화(단기 기억)는 길수록 비싸고 세션이 끝나면 사라진다. 다음 세션은 레포 문서(장기 기억)에 정리해 둔 것만 읽고 이어 간다. 이어 가는 품질은 무엇을 어떤 형태로 남겼느냐에 달려 있다.

| 구분 | 단기 기억 (한 번의 실행 안) | 장기 기억 (회차를 넘어) |
|---|---|---|
| 이미 있는 것 | 도구 루프의 대화, 앞서 확정한 배정을 다음 건 도구에 넘기기, 반려 사유를 돌려주는 재시도 | `params.yaml` 버전, `domain-spec.md`, 개선안 승인·반려 이력과 사유, 발견 판정(`labels`), 분석 리포트 |
| 비어 있는 것 | – | 장기 기억이 다음 회차 에이전트 입력으로 돌아가는 경로 |

설계:

| 구분 | 내용 |
|---|---|

발표와의 연결: "AI가 규칙을 고친다"에 더해 "사람의 판단이 쌓여 다음 회차에 반영된다"를 보여 줄 수 있다. 개선 루프가 반복할수록 나아지는 이유가 된다.

*M12-d 자원 단위 발견 (이 레포, 2026-10-10 완료)*

배경:
- 발견 형식은 **항목(지시서)의 구간**(`slice`)만 담는다. 자원 쪽 패턴은 담을 칸이 없다. P3가 그 예다: 특정 작업자의 가능시간이 수요 시간대와 어긋나 활용률이 낮다.
  - 그래서 분석 에이전트는 지표(`worker_utilization` 낮음)만 적거나, 실험 6.10.1절처럼 선언되지 않은 차원(`worker_id`, `available`)을 구간에 적었다.
  - 지금은 구간 검사가 이런 항목을 빼서 `slice_removed`에 남긴다. "어느 작업자인지"는 설명 문장에만 남는다.
- 그 결과 생기는 빈칸:
  - 채점이 "맞는 작업자를 짚었는가"를 보지 못한다. P3는 지표 이름·방향, 인용 도구, 사람의 원인 확인으로만 맞힌다.
  - 지도에서 그 작업자를 강조할 수 없다.
  - 개선 에이전트가 대상 자원을 구조로 받지 못한다.

설계 (코어 용어는 **자원(resource)**. 코어는 '작업자'를 모른다, 원칙 1):

| 구분 | 내용 |
|---|---|
| 선언 (도메인 파일) | `dimensions.yaml`에 `resources:` 절을 둔다. 예: `worker: {label: 작업자, id_field: worker_id, traits: {available: {label: 가능시간}, skills: {label: 기술}, certs: {label: 자격}}}`. 코어는 이 선언만 읽는다(원칙 2). `DomainPack.dimensions()`가 돌려주는 사전에 키가 하나 늘 뿐이라 `core/interfaces.py`는 그대로다 |
| 발견 형식 | 선택 필드 `resources: {kind: "worker", ids: ["WB01", "WB04"], traits: {"available": ["13:00-18:00"]}}`. `slice`와 함께 쓸 수 있다(예: 지점 B + 작업자 WB01·WB04). 제출 도구의 형식에는 선언된 kind·trait만 둔다 |
| 검사 (코드) | ① kind·trait 이름이 선언돼 있는가. ② id와 trait 값이 **인용한 도구 결과에 그대로 있는가**. 숫자 근거 검사와 같은 원리여서 없는 작업자를 지어낼 수 없고, 인스턴스를 조회하지 않으니 인터페이스도 넓히지 않는다. 어기면 한 번 돌려보내고, 그래도 남으면 그 항목만 빼서 `resources_removed`에 남긴다(구간 검사와 같은 처리) |
| 채점 | 정답 `answer`에 선택 키 `resources: {kind: worker, truth_key: affected_workers, min_precision: 0.5}`를 둔다. 발견이 자원을 적었으면 적은 id 중 정답 자원의 비율이 기준 이상이어야 근거 일치다. 자원을 적지 않은 발견은 지금 규칙(지표 + 도구)대로 채점한다(하위 호환, 저장된 채점은 그대로). 사람 원인 확인(`confirm_cause`)은 유지한다 |
| 관점별 합치기 | 같은 kind이고 id가 겹치며 지표가 같으면 같은 발견이다. 구간이 없는 자원 발견끼리도 합칠 수 있게 된다 |
| 개선 에이전트 입력 | 발견 요약에 `resources`를 넣는다. 예: "WB01·WB04의 가능시간 13~18시". 파라미터로 고칠 수 없는 문제이면 명세·운영 제안으로 가도록 근거를 준다. 작업자 데이터 자체를 고치는 개선안 형식은 범위 밖이다 |
| 화면 | 카드에 "작업자: WB01, WB04 · 가능시간 13:00-18:00" 칩을 단다. 카드를 누르면 지도에서 그 작업자에게 배정된 지시서를 강조한다(결정의 `id_field` 값으로 고름. 지도는 이미 작업자와 배정을 그린다) |
| 기억 (M12-c) | 발견 판정 기억 항목에 자원 요약을 넣는다. 예: "WB01·WB04 저활용 → 원인 틀림" |
| 테스트 (가짜 AI) | 선언 형식 검사, 인용 결과에 없는 id 반려·제거, 채점 정밀도 규칙, 자원 없는 기존 발견의 채점이 바뀌지 않음, 합치기, 제출 형식 |
| 효과 실험 | 같은 규칙 실행(`20261007-123146-440774`), 기억 끔, 단일 3회 + 관점별 3회(약 $0.07). 볼 것: P3 발견이 자원을 채우는 비율, 적은 작업자 중 정답 비율, 지어낸 id(0이어야 함), `slice_removed` 감소 |
| 범위 밖 | 다른 자원 종류(차량 등. 두 번째 도메인이 요구할 때), 자원 데이터를 고치는 개선안, 새 자원 집계 도구(`worker_stats`로 충분) |
| 구현 결과 (2026-10-10) | `core/analysis/resources.py`(선언 검사, 인용 결과 기반 검사·제거, 제출 형식), `analysis_system`(자원 선언이 있을 때만 프롬프트에 자원 칸 안내), `fault_scorer.matches(..., fault)`(정밀도), 관점별 합치기·기억·개선안 입력·화면(칩, 지도 강조). 계획에 더한 것: 중복 값·빈 속성 정리. 실험 결과는 실험 보고서 6.11절 |

완료 기준 (이 레포):
- M12-a: 채점기가 원인 도구를 인용하지 않은 P3 발견을 정답으로 세지 않는다. 제약을 넘긴 개선안 생성에서, 제약을 어긴 안은 "제약 위반"으로 표시되고 위반 내용이 남는다. 제약 형식과 전달 방법이 `handoff.md`에 정리되어 별도 레포가 바로 쓸 수 있다.
- M12-b: 단일 에이전트 대비 관점별 구조의 탐지율·P3 원인 일치·P1 구간 일치를 3회 반복으로 비교한 결과가 실험 보고서에 남는다. 효과가 없으면 효과가 없다는 결론도 결과로 인정한다.
- M12-c: 1회차에서 사람이 내린 판단이 2회차 분석·개선 에이전트 입력에 들어가고, 사용한 기억 버전이 메타데이터에 남는다. 기억 없이/있이 비교한 결과(반려안 재제안, 오탐 재등장)가 실험 보고서에 남는다.
- M12-d: P3 발견이 대상 작업자를 `resources`에 적을 수 있고, 인용 결과에 없는 작업자는 검사에서 걸러진다. 채점이 적은 작업자 중 정답 비율을 본다. 자원 없는 기존 발견의 채점은 바뀌지 않는다. 실험 결과(자원 채움 비율, 정답 비율)가 실험 보고서에 남는다.

# 부록. 구현 명세

## 개요

레포지토리 이름은 **optimization-agent-harness**로 한다. 공통 코어(core)와 도메인 팩(domains)을 한 레포에서 분리 관리하고, 첫 도메인 팩은 출동 스케줄링(dispatch)이다.

**구현 원칙**

- 코어는 도메인을 모른다. 코어 코드에 "작업자", "지시서" 같은 단어가 나오면 경계가 새고 있는 것이다
- 규칙·파라미터·프롬프트는 코드가 아니라 파일(params.yaml, domain-spec.md)에 둔다
- 모든 실행은 seed와 설정 파일로 재현 가능해야 하고, 결과와 트레이스는 실행 ID 단위로 저장한다
- 필수조건 검증은 항상 도메인 팩의 validate()가 최종 판정한다. LLM의 자체 판단을 신뢰하지 않는다

## A2. 공통 코어 모듈

코어는 다섯 묶음이며, 각 모듈은 DomainPack 인터페이스만 통해 도메인에 접근한다.

| 모듈 | 주요 기능 | 입력 → 출력 |
|---|---|---|
| harness/runner | 항목(지시서)마다 LLM 호출 루프 실행, 레벨 설정에 따라 컨텍스트·도구·검증·가드레일·트레이스를 켜고 끔 | 인스턴스, 레벨 → 결정 목록, 트레이스 |
| harness/validator_loop | 결정안을 validate()에 넘기고, 위반 시 사유를 LLM에 돌려 재시도 (최대 N회) | 결정안 → 통과 결정 또는 실패 |
| harness/guardrail | 필수조건 위반 차단, 승인 필요 조건이면 pending 상태로 보류 | 결정 → 확정 / 차단 / 승인 대기 |
| harness/tracer | 단계별 표준 트레이스 레코드 기록 | 이벤트 → 트레이스 파일 |
| llm/client | 모델명·온도·재시도·토큰 집계를 한 곳에서 관리 | 메시지, 도구 → 응답, 사용량 |
| evaluation/runner | 규칙 agent와 AI agent(레벨별)를 같은 seed로 N회 실행 | 실험 설정 → 실행 ID 목록 |
| evaluation/compare | metrics() 결과와 일관성(반복 실행 동일 비율)을 비교표로 생성 | 실행 ID들 → 비교표 JSON |
| evaluation/fault_scorer | 분석 agent가 찾은 패턴을 faults.yaml 정답과 매칭 | 분석 리포트, 정답표 → 탐지율, 오탐 |
| analysis/aggregate_tools | dimensions.yaml에 선언된 차원으로 실패 집계, 조건별 항목 조회 | 결과 레코드 → 집계표 |
| analysis/agent | 집계 도구를 쓰는 LLM agent, 모든 수치에 도구 결과 인용 강제 | 실행 ID → 분석 리포트 |
| improvement/proposer | 분석 리포트를 읽고 params.yaml 변경안 또는 domain-spec.md 수정안 생성 (허용 범위 검사 포함) | 리포트 → 개선안 목록 |
| improvement/simulate | 개선안을 임시 적용해 재실행하고 전후 지표 비교 | 개선안 → 전후 비교 |
| improvement/approval | 승인 시 파일 반영, 버전·이력 기록 | 승인 결정 → 새 버전 |
| storage/store | 실행 메타, 결과, 트레이스, 개선 이력을 SQLite에 저장 | — |

## A3. 도메인 팩 인터페이스와 표준 레코드

코어와 도메인 팩의 계약은 core/interfaces.py 하나에 정의한다. 1주차에 이 파일을 먼저 확정하고 두 사람이 병렬로 작업한다.

```python
# core/interfaces.py
from dataclasses import dataclass, field
from typing import Any, Literal, Protocol

@dataclass
class DecisionRecord:            # 표준 결과 레코드
    item_id: str                 # 예: 지시서 ID
    decision: dict[str, Any] | None   # 예: {"worker_id": "W07"}
    status: Literal["success", "failed", "blocked", "pending_approval"]
    reason_code: str | None      # dimensions.yaml에 선언된 사유 코드
    evidence: str                # 판단 근거 (사람이 읽는 문장)
    dims: dict[str, str]         # 분석 차원 값: {"branch": "B", "hour": "09"}
    metrics: dict[str, float] = field(default_factory=dict)

@dataclass
class TraceRecord:               # 표준 트레이스 레코드
    run_id: str
    item_id: str
    step: int
    kind: Literal["llm", "tool_call", "validate", "retry", "guardrail", "approval"]
    input: Any
    output: Any
    ts: float

@dataclass
class Violation:
    item_id: str
    rule: str                    # 예: "skill_required"
    message: str

class DomainPack(Protocol):
    name: str
    def generate(self, seed: int, faults: list[str]) -> tuple[Any, dict]: ...
    def items(self, instance: Any) -> list[str]: ...
    def solve(self, instance: Any, params: dict) -> list[DecisionRecord]: ...
    def validate(self, instance: Any, decisions: list[DecisionRecord]) -> list[Violation]: ...
    def metrics(self, instance: Any, decisions: list[DecisionRecord]) -> dict[str, float]: ...
    def tools(self, instance: Any) -> list[dict]: ...
    def spec_path(self) -> str: ...
    def params_path(self) -> str: ...
    def dimensions(self) -> dict: ...
```

규칙 agent와 AI agent가 모두 DecisionRecord를 내기 때문에 비교, 분석, UI가 두 agent를 같은 방식으로 다룬다.

## A4. dispatch 도메인 팩

| 파일 | 구현 내용 |
|---|---|
| generator.py | 지점 3개·작업자 30명·지시서 150건/일 × 10일 생성, 격자 좌표, faults.yaml의 패턴(P1~P4)을 켜고 끄는 옵션, 정답표 반환 |
| rule_engine.py solve() | 작업소요 가중치 → 시간·지역 3단계 매칭 → CEI 명장 우선 → 격자 거리 기반 동선 최적, 단계별 근거를 evidence에 기록 |
| rule_engine.py validate() | 기술 미보유, 고위험 자격 없음, 일정 중복, 가능시간 밖 배정을 위반으로 반환 |
| tools.py | find_candidates(order_id, stage), get_travel_time(worker_id, order_id), get_worker_schedule(worker_id), check_assignment(order_id, worker_id) |
| metrics.py | 할당성공률, 평균 이동시간, 희망시간 일치율, 매칭 단계 분포, 작업자 활용률 |
| domain-spec.md | 목적, 필수 조건, 선호 조건, 판단 순서, 예외 처리, 사용 도구 (고정 섹션) |
| params.yaml | 난이도별 가중치, 시간 매칭 범위(0/±30/±60분), 지역 확장 범위(+3/+1/0km), CEI 기준값, 승인 필요 조건. 항목마다 조정 허용 범위(min/max) 명시 |
| faults.yaml | P1 시간대 수요 집중, P2 자격자 편중, P3 가능시간 불일치, P4 경계 지역 수요의 생성 규칙과 정답 설명 |
| dimensions.yaml | 차원: 지점, 시간대, 작업유형, 매체, 건물유형, 난이도, 관할 경계 여부. 사유 코드: NO_SKILL, NO_TIME_MATCH, OUT_OF_AREA, NO_CERT, CAPACITY 등 |

**params.yaml 예시**

```yaml
matching:
  time_window_min: [0, 30, 60]      # 1~3단계
  area_extension_km: [0, 1, 3]
  bounds: {time_window_min: [0, 120], area_extension_km: [0, 5]}
weights:
  difficulty: {pole: 1.5, outdoor: 1.2, high_risk: 1.8}
  building: {house: 1.0, apartment: 1.1}
cei:
  master_threshold: 80
approval_required:
  - matching_stage: 3
  - non_master_for_low_cei: true
```

## A5. 하네스 레벨 설정

레벨은 코드 분기가 아니라 설정 파일로 정의한다. 러너는 이 플래그만 보고 동작하므로, 새 조합(예: 도구 없이 검증만)도 설정 추가로 실험할 수 있다.

```yaml
# configs/harness_levels.yaml
L0: {spec: false, tools: false, validate_loop: false, guardrail: false, trace: minimal}
L1: {spec: true,  tools: false, validate_loop: false, guardrail: false, trace: minimal}
L2: {spec: true,  tools: true,  validate_loop: false, guardrail: false, trace: minimal}
L3: {spec: true,  tools: true,  validate_loop: true,  guardrail: false, trace: minimal, max_retries: 2}
L4: {spec: true,  tools: true,  validate_loop: true,  guardrail: true,  trace: minimal, max_retries: 2}
L5: {spec: true,  tools: true,  validate_loop: true,  guardrail: true,  trace: full,    max_retries: 2}
```

| 플래그 | 꺼졌을 때 | 켜졌을 때 |
|---|---|---|
| spec | 한 줄 지시만 제공 | domain-spec.md를 시스템 프롬프트에 주입 |
| tools | 인스턴스 데이터를 통째로 프롬프트에 넣음 | tools()의 도구만 제공, 데이터는 도구로 조회 |
| validate_loop | LLM 결정을 그대로 채택 | validate() 위반 시 사유를 돌려주고 재시도 |
| guardrail | 위반도 결과에 포함 | 위반 차단, 승인 조건은 pending_approval |
| trace | 최종 결과만 기록 | 모든 LLM·도구·검증 단계 기록 |

L0~L4에서도 비교를 위해 최종 결정에 대한 validate()는 사후 채점용으로 항상 실행하되, 결과에 반영하지 않는다.

## A6. 백엔드 API

모든 엔드포인트는 도메인 이름을 경로에 받아 도메인 무관하게 동작한다.

| 메서드 | 경로 | 기능 |
|---|---|---|
| POST | /domains/{domain}/datasets | seed와 결함 옵션으로 가상 데이터 생성 |
| GET | /domains/{domain}/datasets/{id} | 인스턴스 조회 (지도 표시용) |
| POST | /runs | 실행 시작: agent 종류(rule/ai), 하네스 레벨, 데이터셋, 반복 횟수 |
| GET | /runs/{run_id} | 실행 상태·지표 |
| GET | /runs/{run_id}/decisions | 결정 레코드 목록 |
| GET | /runs/{run_id}/traces/{item_id} | 항목별 트레이스 |
| GET | /runs/{run_id}/stream | 진행 상황 SSE |
| GET | /compare?runs=a,b,c | 비교표 (규칙 vs AI, 레벨별) |
| POST | /analysis | 분석 agent 실행 → 리포트 ID |
| GET | /analysis/{id} | 리포트 (탐지율 채점 포함) |
| POST | /proposals | 리포트 기반 개선안 생성 |
| POST | /proposals/{id}/simulate | 개선안 시뮬레이션 |
| POST | /proposals/{id}/approve | 승인 및 반영 (반려는 /reject) |
| GET | /history | 개선 회차 이력 |

발표용으로 `?cached=true` 옵션을 두어 저장된 실행 결과를 즉시 재생할 수 있게 한다.

## A7. 프런트엔드 화면

탭 4개로 구성하며, 결과 시각화 컴포넌트만 도메인별 어댑터로 교체한다.

| 탭 | 구성 요소 | 사용 API |
|---|---|---|
| 비교 | 좌우 결과 뷰(규칙 / AI), 하네스 토글 L0~L5, 실행 버튼, 지표 패널 | /runs, /runs/{id}/stream, /compare |
| 트레이스 | 항목 클릭 시 단계 카드 타임라인, 규칙 agent 근거 병기 | /runs/{id}/traces/{item_id} |
| 분석 | 패턴 카드, 근거 집계표, 카드 클릭 시 결과 뷰 하이라이트, 탐지율 표시 | /analysis |
| 개선 | 개선안 카드(변경 내용, 전후 지표), 시뮬레이션·승인·반려 버튼, 회차별 추이 그래프 | /proposals, /history |

**도메인 어댑터**: 결과 뷰는 `renderResult(instance, decisions)` 하나만 도메인별로 구현한다. dispatch는 격자 지도(Canvas 또는 SVG), 교대 근무표라면 간트 차트로 바꾸는 식이다.

**구현 방식**: React(Vite) + 차트 라이브러리(Recharts 등). 빌드 결과를 FastAPI가 정적 파일로 서빙해 `python -m api.main` 한 번으로 전체가 뜨게 한다.

**개발 규칙**

- API 키는 .env로 관리하고 커밋하지 않는다. runs/, .env는 .gitignore에 넣는다
- 모든 실행은 run_id, seed, 데이터셋 ID, 레벨, 모델명, params.yaml 버전을 메타로 저장한다
- LLM 호출 결과는 입력 해시 기준으로 캐시해 반복 개발 비용을 줄인다 (최종 측정 때는 캐시 끔)
- params.yaml, domain-spec.md 변경은 개선 루프의 승인을 거친 경우에도 git 커밋으로 남긴다
- 브랜치는 main + 기능 브랜치, PR은 상대 담당자가 리뷰한다

## A9. 테스트 전략

LLM이 없는 부분(생성기, 규칙 엔진, 검증기, 집계)은 결정적이므로 단위 테스트로 확실히 막고, LLM 부분은 평가 러너로 측정한다.

| 대상 | 테스트 내용 |
|---|---|
| generator | 같은 seed면 같은 데이터, 결함 옵션을 켜면 패턴이 통계적으로 드러나는지 |
| rule_engine.solve | 손으로 만든 소규모 케이스(5~10건)의 기대 배정과 일치, 결과에 validate() 위반 0건 |
| rule_engine.validate | 위반 유형별로 일부러 틀린 배정을 넣어 모두 잡아내는지 |
| aggregate_tools | 알려진 결과 레코드에 대한 집계 값 일치 |
| fault_scorer | 가짜 분석 리포트로 탐지율·오탐 계산 검증 |
| DomainPack 계약 | 모든 도메인 팩에 공통 적용되는 계약 테스트 (반환 타입, 필수 파일 존재) — 두 번째 도메인 팩도 이 테스트를 통과해야 함 |
| harness runner | LLM을 가짜 응답(mock)으로 대체해 레벨별 흐름(재시도, 차단, 승인 대기) 검증 |
