# 화면 매뉴얼

브라우저 화면(규칙·데이터 · 비교 · 결정 과정 · 문제 찾기 · 개선 제안 · 에이전트 · Agent workflow · LangGraph agents 탭)의 구성과 사용법이다. 설치와 실행은 [README](../README.md#시작하기)를 본다.

화면에는 쉬운 말을 쓰고, 원래 용어(개발 문서·코드에서 쓰는 이름)는 **마우스를 올리면** 보인다. 대응표는 [11. 용어표](#11-용어표)에 있다.

모든 탭은 **요약을 먼저** 보여주고, 나머지는 **▸ 상세보기 (…)** 를 눌러 펼친다. 괄호 안에 숨은 내용의 양(예: "지표 7개 더 · 미배정 사유")이 적혀 있다. 오른쪽 위 **모두 펼치기**를 켜면 모든 상세보기가 한 번에 열린다(발표·확인용, 브라우저에 기억됨). 정보를 없앤 것은 아니고 접어 둔 것이다.

이 문서의 캡처는 **리허설 번들**(가짜 AI로 미리 만든 결과, API 키 불필요)로 찍었다. 그래서 AI 방식의 판단 근거가 `fake`로 나오고 수치는 AI 성능과 무관하다. 실제 API로 실행하면 같은 자리에 실제 값이 나온다. 지도 배경(OpenStreetMap)은 인터넷이 될 때만 보이며, 캡처는 오프라인 상태라 구 경계만 보인다.

```bash
python -m scripts.rehearsal_bundle              # 리허설 번들 만들기 (몇 초)
python -m api.main --demo demo/rehearsal        # http://127.0.0.1:8000
```

## 1. 화면 구성

![비교 탭 전체](images/ui/01-compare-l0.png)

| 영역 | 내용 |
|---|---|
| 상단 배너 ("저장된 결과 보기"일 때만) | 한 줄: AI 결과는 저장해 둔 것을 다시 보여주고 승인은 임시 사본에만 반영된다. **상세보기**에 저장 정보와 **다시 볼 수 있는 AI 실행 목록**(데이터·레벨·건수) |
| 탭 | 규칙·데이터(규칙과 데이터 보기) 다음, 비교 → 결정 과정 → 문제 찾기 → 개선 제안 순서로 쓰는 것을 전제로 한다. 앞 탭에서 만든 데이터·실행·분석을 뒤 탭이 이어받는다 |
| 데이터 생성 줄 | 데이터 번호(같은 번호면 같은 데이터), **▸ 심어둔 문제: P1·P2·…**(누르면 P1~P4 체크박스), **데이터 생성**, **처리할 건수**, **규칙 방식 실행** |
| 하네스 줄 | 하네스 레벨 L0~L5 선택(버튼마다 새로 켜지는 기능 표시), 지금 레벨에서 켜진 기능(✓/–), **▸ 하네스 설명**(처리 흐름 그림), **AI 방식 실행**, **▸ 반복 N회**(누르면 반복 횟수와 모델·생각 깊이·저장된 응답 재사용 설정) |
| 결론 한 줄 (두 방식 모두 실행 후) | 규칙 방식과 AI 방식의 규칙 위반·배정 성공률·건당 비용을 한 줄로 나란히 |

### 하네스 레벨

같은 AI에 붙이는 장치를 단계별로 늘린다. 레벨 버튼에는 바로 아래 레벨보다 **새로 켜지는 기능**이 붙어 있다(설정 파일 `configs/harness_levels.yaml`에서 자동으로 만든다).

| 레벨 | 업무 규칙 문서 | 조회 기능 | 자동 검사 | 위험 결정 막기 | 과정 기록 | 한 줄 설명 |
|---|---|---|---|---|---|---|
| L0 기본 | – | – | – | – | 최종 결과 | 데이터만 주고 결정하게 한다 |
| L1 +업무 규칙 문서 | ✓ | – | – | – | 최종 결과 | 업무 규칙 문서를 함께 준다 |
| L2 +조회 기능 | ✓ | ✓ | – | – | 최종 결과 | 데이터를 통째로 주는 대신 후보 조회·이동시간·일정 확인 기능을 쓰게 한다 |
| L3 +자동 검사 | ✓ | ✓ | ✓ | – | 최종 결과 | 결정이 규칙을 어기는지 바로 검사하고, 어기면 이유를 돌려줘 다시 시도하게 한다 |
| L4 +위험 결정 막기 | ✓ | ✓ | ✓ | ✓ | 최종 결과 | 규칙을 어긴 결정은 막고, 사람 승인이 필요한 조건이면 승인 대기로 둔다 |
| L5 +과정 기록 | ✓ | ✓ | ✓ | ✓ | **모든 단계** | L4 + AI 응답·조회·자동 검사·다시 시도를 모두 기록한다 (결정 과정 탭에서 볼 수 있다) |

#### 하네스 설명 (처리 흐름 그림)

하네스 줄의 **▸ 하네스 설명**을 누르면 선택한 레벨에서 AI가 지시서 하나를 처리하는 흐름이 그림으로 열린다. 레벨 버튼을 바꾸면 그림도 바뀐다.

![하네스 처리 흐름 (L3)](images/ui/11-harness-pipeline.png)

| 부분 | 내용 |
|---|---|
| 단계 ①~⑥ | ① 입력(기본 지시·업무 규칙 문서·데이터) → ② AI 호출(지시서당 최대 호출 수) → ③ 결정 제출(정해진 형식, 모든 레벨) → ④ 자동 검사 → ⑤ 위험 결정 막기 → ⑥ 과정 기록 |
| 꺼진 단계 | 점선·흐리게 표시하고 "꺼짐 · L3부터"처럼 켜지는 레벨을 적는다 |
| 데이터 주는 방식 | 켜고 끄는 것이 아니라 바뀐다: L0·L1은 **데이터 통째로**, L2부터 **조회 기능 N개**. 현재 쪽이 파란 테두리 |
| 다시 시도 화살표 | ④ 아래에서 ②로 되돌아가는 화살표. 자동 검사가 켜진 레벨(L3~)에서만 색이 있다 |
| 마지막 규칙 검사 | 모든 레벨에서 최종 결정이 규칙을 어겼는지 다시 검사해 센다. 결과는 바꾸지 않고 비교표의 규칙 위반 건수가 된다 |
| 단계 설명 | 단계를 누르면 아래에 하는 일, 설정 위치(파일), 결과에서 보이는 곳이 나온다. ① 입력은 조회 기능 목록(이름·설명)도 보여준다 |
| 레벨별 단계 표 | L0~L5 × 단계(●/○). 현재 레벨 행이 강조되고, 행을 누르면 그 레벨로 바뀐다 |

### 처리할 건수

- **1일차 앞 10건 (시범)**: AI 비용을 확인하는 첫 실행용. 리허설 번들의 AI 결과도 이 건수다.
- **N일차 (150건)**: 하루치.
- **전체 1500건**: 10일치. 규칙 방식은 비용이 없으니 전체로 돌려도 된다.

AI 방식을 실행하면 **같은 건수로 규칙 방식도 함께 실행**되어 왼쪽(규칙 방식)과 오른쪽(AI 방식)을 나란히 비교한다.

## 2. 규칙·데이터 탭 (읽기 전용)

규칙 방식이 판단에 쓰는 **규칙과 데이터**를 본다. 여기서는 아무것도 바꾸지 않는다. 규칙은 개선 제안 탭에서 제안을 승인해야만 바뀐다. 위쪽 버튼으로 섹션을 고른다.

| 섹션 | 내용 |
|---|---|
| 개요 | 규칙 설정값 버전, 지켜야 할 규칙·분석 조건·심어둔 문제 수, 파일 위치와 역할, 현재 데이터 |
| 규칙 설정값 | `params.yaml` 묶음별 표: 현재 값, 바꿀 수 있는 범위(최솟값=최댓값이면 "고정"), 설명. 특정 조건에만 적용하는 규칙 목록과 승인 이력(버전 변화) |
| 지켜야 할 규칙·미배정 사유·분석 조건 | 지켜야 할 규칙(어기면 배정 무효), 미배정 사유(공통 사유 포함), 결과를 나눠 보는 분석 조건 |
| 업무 규칙 문서 | `domain-spec.md`의 6개 부분. L1 이상에서 AI 방식에게 이 문장이 그대로 전달된다 |
| 데이터 | 지점·작업자·지시서 표 (검색, 드롭다운 필터, 머리글 눌러 정렬, 100건씩 더 보기). **행을 누르면 오른쪽 지도에서 위치를 강조하고 그곳으로 이동한다**: 지시서는 그날의 지시서와 함께, 작업자는 출발 위치, 지점은 관할 구역 |
| 심어둔 문제 | P1~P4의 이름과 결과에 나타날 현상. **정답 보기**를 누르면 심는 방법과 채점 기준이 보인다 (발표 중에는 분석 장면 뒤에 연다) |

![규칙 설정값](images/ui/08-domain-params.png)

![데이터 표와 지도](images/ui/09-domain-data.png)

![심어둔 문제 (정답 가림)](images/ui/10-domain-faults.png)

## 3. 비교 탭

### 지도 (서울 강남3구)

![지도와 판단 근거](images/ui/03-map-detail.png)

| 표시 | 뜻 |
|---|---|
| 색칠된 구역 | 지점별 관할 구역. 파랑 = 서초지점(A), 주황 = 강남지점(B), 초록 = 송파지점(C) |
| ▪ 작은 사각형 | 작업자 출발 위치 (지점 색) |
| ● 원 | 배정된 지시서 (지점 색) |
| ✕ 빨간 X | 미배정 또는 위험 결정 막기로 차단 |
| ◯ 노란 테두리 | 승인 대기 (L4·L5) |
| 선 | 작업자의 당일 동선 (출발 위치 → 배정된 지시서를 시작 시각 순으로) |

- **날짜**: 처리할 건수에 포함된 날만 고를 수 있다.
- **배경 지도**: 인터넷이 되면 OpenStreetMap이 흐리게 깔린다. 체크를 끄면 구 경계만 보인다.
- 지도는 `+`/`−` 버튼으로 확대하고 드래그로 이동한다(스크롤 확대는 페이지 스크롤과 겹쳐서 껐다).
- 점에 마우스를 올리면 지시서·작업자 요약이 뜨고, **지시서를 클릭하면 아래에 판단 근거**가 나온다. 규칙 방식은 후보가 어떻게 줄었는지(지점 → 기술 → 자격 → 조건 완화 단계)를 문장으로 남긴다.
- 관할 구역 밖(경계 너머)에 찍힌 지시서는 P4(경계 지역 수요) 문제다. 관할 밖 거리가 가장 많이 완화한 범위보다 멀면 "갈 수 있는 거리 밖"으로 미배정된다.

### 지표 카드

처음에는 핵심 카드 3개(**규칙 위반 · 배정 성공률 · 건당 비용**)만 보이고, 나머지 지표·건당 처리 시간·미배정 사유 그래프·어긴 내용 표는 **상세보기**에 있다. 카드 이름에 마우스를 올리면 원래 용어와 계산 방식이 보인다.

| 지표 | 계산 |
|---|---|
| 규칙 위반 | 레벨과 관계없이 모든 결정을 같은 기준으로 다시 검사한 위반 건수. 0건이 목표 |
| 배정 성공률 | 배정된 지시서 ÷ 전체 지시서 |
| 희망시간 준수율 | 배정된 지시서 중 고객 희망시각에 정확히 시작한 비율 |
| 평균 이동시간 | 직전 위치에서 지시서까지 이동시간(직선거리 × 우회계수 1.3 ÷ 평균 30km/h)의 평균 |
| 작업자 가동률 | 작업 시간 합 ÷ 작업자 가능시간 합 |
| 조건 그대로 / 조금 완화해 / 많이 완화해 배정 | 배정 건 중 시간·지역 조건을 완화하지 않고, 한 단계 완화해서, 최대로 완화해서 배정한 비율 |
| 건당 비용·처리 시간 | AI는 AI 호출 비용, 규칙 방식은 $0 |

아래 막대그래프는 미배정 사유("자격 보유자 없음", "일정이 꽉 참", "갈 수 있는 거리 밖" 등)별 건수다. 막대에 마우스를 올리면 설명 문장과 사유 코드가 보인다.

### 레벨별 비교표

![레벨별 비교표](images/ui/02-compare-table.png)

같은 데이터·같은 건수로 실행한 규칙 방식과 AI 방식(레벨별)을 한 줄씩 비교한다. 요약 표는 규칙 위반·배정 성공률·건당 비용만, **상세보기**를 펼치면 실행 횟수·다른 지표·반복 시 같은 결과·건당 시간까지 모든 열이 나온다. 위 캡처에서 L0은 규칙 위반 2건이 남고 L3·L5는 자동 검사 덕분에 0건이다. **반복 시 같은 결과**는 같은 레벨을 2회 이상 반복 실행했을 때 모든 실행에서 결정이 같은 지시서의 비율이다.

## 4. 결정 과정 탭

![결정 과정](images/ui/04-trace.png)

AI 방식이 지시서 하나를 어떻게 결정했는지 단계별로 본다. **단계 기록은 과정 기록이 켜진 레벨(L5) 실행에만 있다** (L0~L4는 최종 결정만 기록).

1. **실행**을 L5로 고른다.
2. 필터로 좁힌다: 전체 / **다시 시도한 건** / 차단·승인 대기 / 미배정.
3. 왼쪽 목록에서 지시서를 고르면 맨 위에 **결론 카드**, 그 아래 AI 방식과 규칙 방식의 최종 결정이 나란히, 그 아래 **단계 흐름 한 줄**이 나온다.
4. 단계별 내용(AI 응답 원문, 조회 결과, 토큰)은 **상세보기**를 펼쳐 본다(캡처는 펼친 상태).

| 요약 | 뜻 |
|---|---|
| 결론 카드 | 지시서 · AI 방식의 최종 상태(배정 / 미배정 / 차단 / 승인 대기) · **규칙 방식과 같은 결정인지** · 다시 시도 횟수 · 자동 검사에서 걸린 횟수 |
| 단계 흐름 한 줄 | 예: `AI 응답 → 자동 검사 ✕ → 다시 시도 → AI 응답 → 자동 검사 ✓ → 위험 결정 막기 ✓`. 같은 단계가 이어지면 `조회 ×3`처럼 묶는다 |

| 단계 | 뜻 |
|---|---|
| AI 응답 | AI가 요청한 조회·결정. 사용한 토큰 수 표시 |
| 조회 | 후보 조회·이동시간·일정 확인 등의 입력과 결과 |
| 자동 검사 | 결정이 규칙을 어기는지 검사한 결과 (✕ 어긴 규칙과 내용 / ✓ 규칙 위반 없음) |
| 다시 시도 | 자동 검사가 돌려보내며 AI에게 준 메시지 |
| 위험 결정 막기 | 확정 / 차단 / 승인 대기 |

## 5. 문제 찾기 탭

![문제 찾기](images/ui/05-analysis.png)

AI 분석이 실행 결과를 여러 조건으로 집계해 보고 반복되는 문제와 추정 원인을 낸다. 심어둔 문제(P1~P4)를 찾는지 정답과 대조한다.

1. **규칙 방식 전체 실행** (1500건, 비용 없음) → **분석할 결과**에서 고른다.
2. **AI 분석 실행**.

맨 위 **결론 한 줄**에 "심어둔 문제 4개 중 3개 찾음 (75%)", 문제별 ✓/✕, 사람 확인 대기 건수가 나온다. 찾은 문제는 카드마다 **제목, 정답 일치 여부(또는 사람 확인 버튼), 조건 칩**만 먼저 보이고 설명·추정 원인·근거 데이터는 카드의 **상세보기**에 있다. 아래 표의 수치 카드는 결론 줄 아래 **상세보기 (정답 대조 · 분석 비용·시간)**에 있다.

| 요소 | 뜻 |
|---|---|
| 찾아낸 비율 (정답 대조) | 심어둔 문제 중 찾은 비율. 정답은 채점에만 쓰며 AI 분석은 보지 못한다 |
| 정답에 없는 문제 | 정답에 없는 찾은 문제. 사람이 **맞는 문제 / 잘못 짚음**으로 확인한다 (확인 대기 건수 표시) |
| 잘못 짚음 (사람 확인) | 사람이 잘못 짚었다고 확인한 건수 |
| 분석 비용·시간 | AI 호출 수, 집계 횟수, 비용 |
| ✓/?/✕ 문제 (결론 줄) | 심어둔 문제별로 찾았는지. **?**는 근거는 맞고 원인 확인을 기다리는 문제(아래). 마우스를 올리면 일치한 찾은 문제 ID |
| 원인 확인 (찾은 문제 카드) | 원인 해석이 중요한 문제(예: P3 가능시간 불일치)는 근거가 정답과 맞아도 바로 찾은 것으로 세지 않는다. 카드의 **원인 맞음 / 원인 틀림**으로 사람이 판정해야 ✓ 또는 ✕가 된다 |
| 찾은 문제 카드 | 제목, 조건 칩(예: "관할 경계 여부: 경계 지역", 마우스를 올리면 원래 값), 미배정 사유. 상세보기에 수치 설명, 추정 원인, **근거 데이터**(AI가 인용한 집계와 결과 표) |

- 찾은 문제의 제목을 누르면 **오른쪽 지도에서 해당 조건의 지시서만 강조**되고 나머지는 흐려진다. 강조된 지시서가 가장 많은 날짜가 자동으로 선택된다.
- 찾은 문제의 숫자는 인용한 집계 결과에 실제로 있는 값이어야 한다. 근거가 확인되지 않은 것은 "근거 숫자가 확인되지 않아 뺀 찾은 문제"로 따로 모인다.
- **자원 칩**(예: "작업자: WB01, WB04 · 가능시간 13:00-18:00"): 그 문제가 특정 자원에 대한 것일 때 나온다. 제목을 누르면 지도에서 그 자원이 맡은 지시서가 강조된다(조건 칩도 있으면 둘 다 맞는 지시서). AI가 적은 자원 중 근거 데이터에서 확인되지 않은 것은 빠지고, 상세보기에 "자원에서 뺀 항목"으로 나온다.

  ![자원 발견을 눌러 그 작업자가 맡은 지시서를 강조한 모습](images/ui/16-analysis-resource-map.png)

- **관점별로 분석**(AI 분석 실행 옆 체크): 실패 패턴·자원 활용·시간 수급 관점마다 AI를 따로(동시에) 돌린 뒤 합친다. 비용은 관점 수만큼 늘어난다(약 3배).
  - 카드: "관점: …" 칩은 그 문제를 찾은 관점이다. "관련: F…" 칩은 구간이 겹치는(한쪽이 더 좁은) 다른 문제다. 여러 관점이 같은 문제를 찾았으면 상세보기에 **다른 관점의 해석**이 나란히 나온다. 어느 해석이 맞는지는 사람이 판단한다.
  - 상세보기 (정답 대조 · 분석 비용·시간): 관점별 카드에 발견 수, 비용, 시간, 실패가 나온다. 한 관점이 실패해도 나머지 관점으로 리포트가 나온다.

### 규칙 설정값: 분류와 민감도 (M13)

![규칙 설정값: 분류 배지, 민감도, 변경 이력](images/ui/19-params-map.png)

규칙·데이터 탭의 **규칙 설정값** 표에는 다음이 함께 보인다.
- **분류 배지**: 정책(AI 제안이 바꿀 수 있음) / 추정값 / 고정 / 통제.
- **배정 성공률 범위·정시 배정 비율 범위**: 지금 데이터로 그 값을 허용 범위 안에서 바꿔 돌렸을 때의 최소~최대(건수)다. "변화 없음"이나 "(0~3 변화 없음)"은 그 구간에서 움직여도 결과가 같은 손잡이다. 비교 탭에서 데이터를 만들어야 계산한다(AI 비용 0).
- **변경 이력**: 승인으로 규칙 버전이 오를 때마다 카드 하나다. 바뀐 값(전→후), 근거 문제, 전후 지표, 승인자, 사유가 나온다. 이전 기록에 없는 값은 "기록 없음"이다.

## 6. 개선 제안 탭

![개선 제안과 미리 돌려보기](images/ui/06-improve-simulation.png)

분석 결과를 바탕으로 규칙을 어떻게 바꿀지 제안을 만들고, 미리 돌려봐 효과를 확인한 뒤 사람이 승인한다.

1. **개선 제안 만들기** (문제 찾기 탭에서 만든 분석 결과 기준).
2. 제안마다 **미리 돌려보기** → 카드 제목 아래 **요약 한 줄**에 배정 성공률 전 → 후(변화), **나빠진 지표**(없으면 "나빠진 지표 없음"), 규칙 위반 건수가 나온다. 근거·바꿀 내용·전·후 전체 지표 표는 카드의 **상세보기**에 있다.
   - 규칙 설정값(params.yaml)을 바꾸는 제안은 규칙 방식을 다시 계산해 바로 비교한다(비용 없음).
   - 업무 규칙 문서(domain-spec.md)를 고치는 제안은 AI 방식을 고치기 전·후 문서로 실행해야 하므로 **예상 비용을 먼저 보여주고 확인을 받는다**. 레벨과 건수를 고를 수 있다.
3. 메모를 적고 **승인** 또는 **반려**.

| 제안 상태 | 뜻 |
|---|---|
| 제안됨 | 미리 돌려보기 전 |
| 적용 불가 | 바꿀 수 있는 범위(params.yaml의 bounds) 밖이거나 형식 오류. 이유가 빨간 글씨로 나온다 |
| 미리 돌려보기 완료 | 승인할 수 있다 |
| 승인됨 / 반려됨 | 결정 완료. 승인하면 규칙 설정값 버전이 오른다 |
| 기준이 바뀜 | 다른 제안이 먼저 승인되어 기준 파일이 바뀌었다. 다시 제안해야 한다 |

- 제안 종류: **규칙 설정값**(값 변경, 또는 "경계 지역만"처럼 특정 조건에만 적용) / **업무 규칙 문서**(부분 교체, 현재·제안 비교 펼침).
- **기억**: 반려 사유와 문제 찾기의 판정(잘못 짚음, 원인 맞음·틀림)은 다음 회차 AI 입력으로 돌아간다. 개선 제안 탭의 **기억** 펼침에서 다음 회차에 알려 줄 내용을 볼 수 있고, 제안 묶음과 분석 결과에 "사용한 기억 n건"이 표시된다. 규칙 버전이 바뀐 뒤의 기억은 "이전 규칙(vN) 기준"으로 표시된다. 그래서 **반려할 때 메모(사유)를 적는 것이 중요하다.**
- **제약 위반**: 개선 제안을 만들 때 사람이 정한 한도(예: "관할 확장 4km까지", "정시 배정 비율 감소 3%p까지")가 함께 주어졌다면, 상단에 **적용한 제약** 목록(누가, 왜)이 펼침으로 나오고, 미리 돌려본 결과가 한도를 넘는 제안에는 **⚠ 제약 위반** 배지와 내용이 붙는다. 승인은 막지 않으며 사람이 판단한다. 제약은 이 화면에서 입력하지 않고 API(`POST /proposals`의 `constraints`)로 받는다.
- **저장된 제약** (M15 후속): agents 탭에서 현장 의견을 정리해 확정한 제약 목록(의견 원문, 확정한 곳, 규칙 버전). 켜진 제약은 **개선 제안 만들기**에 자동으로 더해지고(요청의 제약과 같은 한도는 하나만), 제안 묶음의 "적용한 제약"에 "그중 저장된 제약 n개"로 표시된다. 지금 규칙과 맞지 않는 저장 제약(없어진 파라미터 등)은 빼고 쓴다. **끄기·켜기**로 고른다.
- **승인은 파일에만 반영한다. git 커밋은 사람이 직접 한다.** "저장된 결과 보기"에서는 임시 사본에만 반영되고, 서버를 다시 켜면 처음 상태로 돌아간다.
- 상단 한 줄: 반영·반려 횟수와 마지막 개선 한 바퀴의 비용·시간. **상세보기**에 개선 한 바퀴에 AI가 쓴 시간·비용, 같은 분석을 사람이 할 때의 추정 시간(직접 입력, 브라우저에만 저장) 카드가 있다.

- **승인자**: 승인 버튼 옆 칸에 이름을 적으면(선택) 변경 이력 카드에 남는다. 로그인이 없어 직접 적고, 이 브라우저에 기억된다.
- **적용 불가 (분류)**: 추정값(작업소요·가중치·이동 속도), 고정값, 통제 설정(승인 조건)을 바꾸는 제안은 허용 범위 안이어도 적용 불가다. 사유가 분류별로 나온다(예: "추정값은 실적 근거로만 사람이 바꾼다").

### 제시 기준: 순위·참고·최소 변경 추천 (M15-A)

제안이 많으면 사람이 다 볼 수 없다. 개선 탭은 코드로 정한 기준대로 **본안 최대 3건**을 순위대로 보여 주고 나머지는 접는다 (기준값은 `configs/proposals.yaml`, 핵심 지표와 방향은 도메인 `dimensions.yaml`의 `metrics`).
- 순위는 미리 돌려본 결과로 매긴다. **설정값 제안 N건 모두 미리 돌려보기** 버튼으로 한 번에 돌린다(규칙 엔진, AI 비용 0). 아직 돌리지 않은 제안은 순위 없이 아래에 있다.
- 정렬: ① 사람 제약을 지키는 안 → ② 핵심 지표 개선폭이 큰 순 → ③ 나빠진 지표의 하락폭이 작은 순.
- 카드 제목 앞의 **N순위** 칩, 요약 아래 **순위 이유** 한 줄 (제약 지킴 여부, 핵심 지표 변화, 나빠진 지표).
- **참고 (접음)**: 적용 불가, 규칙 위반 증가, 핵심 지표 개선 없음, 최소 효과(+1%p) 미만, 같은 발견의 아랫순위 안(발견 하나당 1건), 개수 상한으로 잘린 안, **지배당한 안**(모든 지표에서 다른 안보다 나쁜 안). 펼침 제목에 실제로 있는 분류와 건수만 나오고(예: "참고 2", "잘림 1 · 참고 1"), 카드마다 접힌 이유가 나온다.
- **최소 변경 추천**: 숫자 하나를 바꾸는 제안이면 현재 값과 제안 값 사이를 규칙 엔진으로 훑어 **같은 핵심 지표를 내는 가장 작은 값**을 요약 줄에 보여 준다. 예: 관할 밖 5km 제안 → "최소 변경 추천: matching.area_extension_km[2] 3 → 4 (제안값 5일 때와 핵심 지표 같음)".
- 득실 지도의 개선안 점에도 "1순위", "안2 (참고)"처럼 순위가 붙는다.

### 실적 (가상 고객 반응) (M17)

미리 돌려보기가 끝난 **규칙 설정값** 개선안 카드에 "실적 (가상 고객 반응)" 표가 자동으로 붙는다(처음 2~3초 계산). 계획(규칙 엔진 배정)에 현실 모델의 고객 반응(수락·불만·일정 재요청·취소)과 날짜 이월을 붙여 만든 실적을 **현재와 이 안**으로 나란히 보여 준다. "계획 지표가 좋아져도 고객 기준으로는 나빠질 수 있다"를 승인 전에 보기 위한 것이다.

| 줄 | 뜻 |
|---|---|
| 계획 · 배정 / 정시 배정 | 규칙 엔진이 배정한 건, 희망 시각에 정확히 시작하도록 배정한 건 (계획) |
| 실적 · 약속 준수 | 원래 희망 날짜에, 희망 시각 ±60분 안에 완료된 건 (실적). 계획의 "정시 배정"과 다르다 |
| 실적 · 불만율 / 취소율 / 미처리율 | 완료됐지만 불만, 고객 취소 또는 이틀 넘게 밀려 취소, 마지막 날까지 처리되지 못함 (전체 지시서 대비) |
| 실적 · 평균 이월 | 다음 날로 넘어간 횟수의 평균 |
| 차이 | 이 안 − 현재. 좋아지면 초록, 나빠지면 빨강 |
| 계획과 달라진 지시서 | 처음 달라진 이유별 건수: **같은 날 재배정**(이월 건이 들어온 날은 그날 전체를 다시 배정해 원래 날 첫 시도부터 달라짐) · **이월**(계획 자체가 배정 실패) · **재요청**(계획대로 갔지만 고객이 일정 재요청) |

- **참고용**이다. 승인 조건·순위·검사에 쓰지 않고, AI에게도 보여 주지 않는다(분석·개선안 입력, 미리 돌려보기 결과, 순위 사유, 검색 색인 어디에도 들어가지 않는다).
- 현실 모델(보통·관대·민감)을 바꿔 볼 수 있다. 실적 seed 1~5 평균이고, 현재와 이 안은 같은 seed(같은 고객 난수)를 쓴다.
- 계획 숫자는 1일차부터의 계획이다. 이월 건이 섞인 날은 그날 전체를 다시 배정하므로, 2일차 이후 실제로 실행된 계획과 다르다(같은 날 재배정 건수로 드러난다).
- 업무 규칙 문서 개선안은 대상이 아니다(AI 배정 실행이라 이월 재배정을 규칙 엔진이 하면 섞인다). 실적 기능이 없는 도메인은 표가 나오지 않는다.
- 저장된 결과 보기(리허설)에서도 실제로 계산한다(AI 호출 없음). 저장하지 않으므로 다시 열면 다시 계산한다.

### 득실 지도

![득실 지도: 탐색 점, 현재 버전, AI 개선안, 제약선](images/ui/17-tradeoff-map.png)

개선 탭 위쪽의 산점도다. 파라미터를 바꿔 가며 규칙 방식으로 돌린 결과(**탐색 점**), **현재 버전**(검은 마름모), **AI 개선안**(주황, 안1·안2…), 사람이 정한 **지표 제약선**(빨간 점선)을 한 장에 그린다.
- 규칙 방식만 쓰므로 AI 비용이 들지 않는다.
- 기본 축은 가로 = 배정 건수, 세로 = 정시 배정 건수다(비율 × 전체 건수). "건수로 보기"를 끄면 비율로 본다.
- **축 1·축 2**로 탐색할 파라미터를 고르고 **탐색**을 누른다. 조합은 최대 50개다. 결과가 같은 조합은 한 점으로 겹친다(표로 보기에 모두 있음).
- 점에 마우스를 올리면 파라미터 값과 지표, 규칙 위반이 보인다. 개선안 점을 누르면 그 제안 카드로 이동한다.
- 추정값(예: 이동 속도)을 축으로 고르면 점이 **경고 색 삼각형**이 되고 경고 문장이 나온다. 지표가 좋아져도 가정만 바뀐 것이다.

## 6.4b 에이전트 소개 탭

실행 없이 핵심 에이전트를 설명하는 탭(발표·처음 보는 사람용). 위에서부터 AI·코드·사람의 역할, 흐름(배정 → 분석 → 개선 → 사람 검토 → 반영, 의견 정리·Supervisor), 에이전트 카드 다섯(배정·분석·개선·의견 정리·Supervisor: 역할, 받는 것 → 내는 것, 쓰는 도구, 코드가 지키는 것, 사람이 하는 일, 지금 설정된 모델), 하네스 레벨 L0~L5(더하는 것, 에이전트가 하는 일, 그래프에 붙는 노드, 지금 설정), LangGraph 구성(서버가 만든 상위 그래프를 고정 흐름·Supervisor 지휘로 바꿔 보기, 에이전트 하위 그래프 설명), 공통 안전장치(반복 실패·도구 실패·예산 초과·근거 부족·해결 불가). 모델 이름과 레벨 설정만 서버에서 읽고 나머지는 고정 설명이다.

## 6.5 에이전트 탭 (M16)

핵심 에이전트(배정, 분석, 개선, 의견 정리, Supervisor)를 **하나씩** 실행하고, 그 에이전트가 일하는 과정(AI 판단 → 도구 사용 → 검사)을 한 화면에서 본다. 여러 에이전트를 이어서 돌리는 흐름은 LangGraph agents 탭(8장)이 한다.

| 영역 | 내용 |
|---|---|
| 왼쪽 위 | 에이전트 고르기(카드에 지금 설정된 모델) |
| 왼쪽 입력 | 배정: 지시서 건수(1~10), 하네스 레벨(기본 L5). 데이터 번호·심어둔 문제는 비교 탭 설정을 쓴다 / 분석: 규칙 실행 결과(데이터 번호 · 심어둔 문제 · 범위 · 설정 버전), 관점별로 분석. **지금 조건으로 규칙 방식 실행**은 비교 탭의 데이터 번호·심어둔 문제로 전체 실행을 고른다(같은 조건·지금 설정 버전의 실행이 있으면 그것을 고르고, 없으면 새로 만든다. 규칙 엔진만 써서 비용 0) / 개선: 분석 리포트, 저장된 제약 사용 / 의견 정리: 개선안, 의견 한 줄 / Supervisor(M18): 규칙 실행 결과(분석과 같은 목록·버튼), 저장된 제약 사용 |
| 실행 | 위 **저장된 AI 응답 재사용 (캐시)** 체크박스: 서버 전체 설정이고 다음 실행부터 적용된다. 켜면 AI에게 보내는 입력이 이전과 똑같을 때 저장된 응답을 그대로 쓴다(비용 0, 결과도 같다). 끄면 매번 실제로 부른다(`POST /llm/cache`, 환경변수 `LLM_CACHE`와 같다). 요약 줄의 "(캐시 14/14)"는 저장된 응답을 쓴 호출 수. 누르면 먼저 **제공사·모델·생각 깊이·호출 상한·캐시 상태**를 보여 주고 확인을 받는다. 실패하면 사유와 함께 **최근 저장된 실행 보기**를 띄운다 |
| 끝난 실행 | 같은 에이전트의 지난 실행 목록. 누르면 저장된 기록으로 다시 본다(API 호출 없음, 발표 재생용) |
| 오른쪽 요약 | 입력 → 출력 한 줄, 제공사·모델(deployment), 호출 수, 토큰(입력 + 캐시 / 출력), 시간, 비용(단가가 없으면 미확인). 끝난 분석에는 **문제 찾기 탭에서 보기** 버튼: 그 리포트를 문제 찾기 탭에 열어 발견 카드·근거 데이터·지도 강조·사람 판정을 쓴다(다시 분석하지 않아 비용 없음). 끝난 개선에는 **개선 제안 탭에서 보기** 버튼: 그 개선안 묶음을 개선 제안 탭에 열어 개선안 카드·순위·미리 돌려보기·실적 비교·사람 승인을 쓴다(비용 없음) |
| 처리 흐름 | agents 탭과 같은 LangGraph 하위 그래프를 쉬운 이름으로 보여 준다(AI 판단·도구 사용·결정 받기·규칙 위반 검사·다시 시도·위험 결정 확인·기록·재요청 등). 카드에 마우스를 올리면 그 단계 설명. 노드마다 지나간 횟수와 마지막 내용, 실행 중이면 지금 노드 강조. **기술 정보 보기**를 켜면 원래 이름과 노드 종류·id(agents 탭과 같은 표시). 실선은 항상 이어지는 단계, 점선은 조건에 따라 고르는 갈림길(그래프 아래 범례) |
| 진행 기록 | 줄마다 몇 번째 AI 응답인지와 종류: **AI 판단**(요청한 도구, 같은 도구를 여러 번이면 ×N), **도구 사용**(쉬운 도구 이름 · 입력 요약 → 결과 받음/오류), **✓/✕/↻ 검사**(규칙 위반 검사·다시 시도·위험 결정 확인·근거 검사·개선안 검사·제약 형식 검사와 사유), **결정**(배정 내용 또는 못 한 사유), **■ 끝난 이유**(결과 제출·호출 한도 등). 배정은 지시서마다 ▸ 머리줄로 나뉘고, 관점별 분석은 줄마다 관점 이름이 붙는다. 원래 도구 이름·입력·결과 JSON은 줄 끝 **자세히**를 펼쳐 본다. 실행 중에는 한 줄씩 쌓인다 |

- 실행은 기존 API를 그대로 쓴다(배정 `POST /runs`, 분석 `POST /analysis`, 개선 `POST /proposals`). 의견 정리만 단독 API(`POST /agent-tab/opinion`)이다. 결과는 제약 확인 전 단계까지이고, 정리한 제약이 의견과 맞으면 요약 아래 **제약 확정해 저장**으로 저장한다(`POST /agent-tab/opinion/{id}/save`, 형식은 코드가 다시 검사, LangGraph agents 탭의 제약 확인과 같은 일). 저장한 제약은 개선 제안 탭 저장된 제약 목록에 출처 agent-tab으로 들어가고, 다음 개선안 요청·LangGraph agents 실행·Supervisor가 "저장된 제약 사용"으로 불러온다. 의견은 문서 검색 색인에 현장 의견으로도 남는다. 저장 전에는 개선안에 영향이 없다.
- 배정의 단계 기록은 L5에만 저장된다. 다른 레벨은 실행 중에는 타임라인이 보이지만, 끝난 뒤 다시 보면 최종 결정만 남는다.
- 쉬운 이름: 코어 도구(집계·개선안·문서 검색·제출)와 그래프 노드 이름은 `web/src/components/agentTerms.ts`, 도메인 도구 이름·입력 이름은 도메인 어댑터의 `toolNames`·`argNames`(배정은 `web/src/domains/dispatch/index.ts`), 묶는 기준 이름은 도메인 `dimensions.yaml`의 label을 쓴다. 표에 없는 이름은 원래 이름 그대로 나온다. 저장된 기록은 바꾸지 않으므로 지난 실행도 새 표현으로 보인다.
- **Supervisor**(M18): 분석·개선 에이전트와 미리 돌려보기·파라미터 훑기를 도구로 부르며 다음 행동을 스스로 정하고 판단 보고서를 낸다. 요약 아래 **판단 보고서** 카드: 추천안(제목·확신도·핵심 지표 전→후·기대 효과·잃는 것), 사람에게 묻는 것, 접힌 원인 가설·시도 기록·추천하지 않은 안. 판단 보고서 검사에 실패하면 실패 상태(해결 불가·예산 초과 등)와 사유. 처리 흐름은 **Supervisor와 에이전트들** 팀 그림이다: Supervisor에서 분석 에이전트·개선 에이전트·규칙 엔진·문서 검색·보고서 검사로 나가는 요청 선과 돌아오는 보고 선, 카드에는 요청 횟수, 실행 중에는 지금 일하는 쪽이 강조된다. 분석·개선 에이전트 카드를 누르면 그 에이전트의 내부 흐름이 아래에 열린다. 진행 기록은 대화 형식이다: "Supervisor → 분석 에이전트: 질문·구간", 접힌 그 에이전트의 진행, "분석 에이전트 → Supervisor: 발견 N건 …", 규칙 엔진 보고에는 진단 신호와 핵심 지표 전→후. 사용량은 부른 에이전트를 포함한 합. 규칙은 바꾸지 않는다(결과는 `supervisor_runs`에 저장, 반영은 개선 탭·LangGraph agents 탭에서 사람이). 호출 상한(도구 40·분석 3·개선 4)과 예산(추정 $1.5·20분)
- 저장된 결과 보기(리허설)에서는 배정·분석·개선이 저장 결과를 재생하고(배정은 데이터 번호 42, P1~P4, 10건, L0·L3·L5), 의견 정리·Supervisor는 가짜 AI로 돈다.

## 7. Agent workflow 탭 (LangGraph)

![Agent workflow: 사람 승인에서 멈춘 모습](images/ui/12-workflow-approval.png)

위 탭에서 하나씩 누르던 단계를 **LangGraph 그래프 하나**로 묶어 한 번에 흘려 본다. 각 단계(에이전트)를 넘어갈 때마다 멈추고, 사람이 **[다음 실행]**을 눌러야 다음 단계로 간다. 흐름만 간단히 보여주는 화면이고, 각 단계의 자세한 결과는 노드의 **[탭에서 보기 →]**로 해당 탭에서 본다(그 탭이 같은 데이터·실행·분석·제안을 이어받는다). 구조와 노드 추가 방법은 [docs/workflow.md](workflow.md).

1. 데이터 번호, 심어둔 문제, 처리할 건수(처리 순서 앞 N건), 하네스 레벨을 고르고 **워크플로우 준비** → 첫 단계(데이터 생성) 앞에서 멈춘다.
2. **[다음 실행 ▶]**을 누를 때마다 한 단계씩 실행되고, 노드 아래에 결과 한 줄이 붙는다.
3. 미리 돌려본 결과 핵심 지표가 좋아지면 **사람 승인**에서 멈춘다 → 메모를 적고 **[승인]** 또는 **[반려]**. 반려하면 다음 제안을 미리 돌려본다.
4. 승인 후 **[다음 실행]** → 반영 → 끝.

| 요소 | 뜻 |
|---|---|
| 노드 색 (왼쪽 띠) | 파랑 = AI 에이전트 (AI 방식 실행, AI 분석, 개선 제안), 회색 = 규칙 계산, 초록 = 사람 |
| 노드 표시 | ○ 대기 · ▶ 다음 · … 실행 중 · ✓ 완료 · ⏸ 사람 승인 대기 · ✕ 실패 (같은 단계 [다시 실행]) |
| ◇ 줄 | 조건부 연결: 결과에 따라 다음 단계가 갈린다 (예: 핵심 지표가 좋아짐 → 사람 승인) |
| 오른쪽 상자 | LangGraph로 만든 구조 설명과 에이전트 추가 예시 코드 |

- 그림은 손으로 그린 것이 아니라 서버가 컴파일한 그래프(`get_graph()`)의 노드·연결이다. 노드를 추가하면 그림에도 바로 나온다.
- LangGraph가 설치되어 있지 않으면 설치 안내(`pip install -e ".[workflow]"`)만 나온다.
- "저장된 결과 보기"에서는 리허설 번들 조건(데이터 번호 42, P1~P4, 10건, L0·L3·L5)으로 실행해야 AI 단계가 저장된 결과를 찾는다.

## 8. LangGraph agents 탭

![LangGraph agents: 배정 에이전트 내부가 실시간으로 진행되는 모습](images/ui/14-agents-live.png)

배정·분석·개선 제안 **에이전트의 내부까지 LangGraph로** 만든 별도 탭이다. 7장(Agent workflow)이 기존 에이전트를 노드로 이어 붙였다면, 여기서는 AI 응답·조회 도구·자동 검사·다시 시도가 모두 그래프의 노드와 연결이다. 결과는 이 탭 안에서만 쓰고(다른 탭·기록에 섞이지 않음), 승인한 제안만 규칙 파일에 반영한다. 구조와 에이전트 추가 방법은 [docs/langgraph-agents.md](langgraph-agents.md).

1. 데이터 번호, 심어둔 문제, 처리할 건수, **하네스 레벨**, **AI**(가짜 AI / 실제 AI), **속도**를 고른다.
   - 하네스 레벨을 바꾸면 **배정 에이전트 내부** 그래프가 바로 다시 그려진다: L0은 AI 응답 → 결정 읽기 → 기록뿐이고, 레벨을 올릴수록 조회 도구 → 자동 검사·다시 시도 → 위험 결정 막기 → 과정 저장 노드가 붙는다.
   - "저장된 결과 보기"에서는 가짜 AI만 쓴다(비용 없음, 수치는 AI 성능과 무관). 실제 AI는 비용이 든다. 실제 AI의 제공사·모델은 서버 설정(`configs/llm.yaml`, `LLM_PROVIDER`)을 따르고, 마우스를 올리면 보인다(예: Azure OpenAI gpt-4.1-mini).
   - 속도는 내부 단계 사이 간격이다(가짜 AI는 너무 빨라 눈으로 따라가기 어렵다).
   - **관점별 분석**을 켜면 분석 에이전트 내부가 "시작 → 관점 노드 3개(동시에) → 합치기"로 다시 그려진다. 진행 기록에 세 관점의 단계가 섞여 쌓인다(동시에 돌기 때문).
2. **에이전트 준비** → 첫 단계(데이터 준비) 앞에서 멈춘다.
3. **[다음 실행 ▶]**을 누르면 다음 단계(에이전트 하나)가 끝까지 실행된다. 실행되는 동안 아래의 에이전트 내부 그래프에서 지금 노드가 강조되고, **방금 지나간 연결이 움직이는 선**으로 표시되며, 노드별 지나간 횟수와 **진행 기록**이 실시간으로 쌓인다.
4. 개선 제안 에이전트가 끝나면 **미리 돌려보기·순위**가 설정값 제안을 모두 돌려보고 제시 기준(6장)으로 순위를 매긴 뒤, **순위대로** 하나씩 **사람 검토**에서 멈춘다. 막대에 회차·순위·순위 이유·최소 변경 추천이 보인다.
5. 사람 검토에서 셋 중 하나 (M15-B):
   - **[승인]** → 반영 → **재배정·재평가**(새 규칙으로 전체를 다시 배정해 회차 전·후를 잰다) → **종료 판정**.
   - **[반려]** → 다음 제안. 남은 제안이 없으면 반려 사유를 기억으로 **다시 제안**받는다 (회차당 `max_reproposals`번, `configs/workflow.yaml`).
   - **[의견 보내기]**: 메모 칸에 한 줄 의견(예: "관할 밖 4km 초과 출동 불가")을 적고 보내면 **의견 정리 에이전트**가 제약 형식으로 바꾸고 코드가 형식을 검사한다. 숫자 한도가 없는 등 형식이 틀리면 사람 검토로 돌아와 **⚠ 의견을 제약으로 정리하지 못했습니다**와 이유를 보여 준다.
   - 정리가 되면 **제약 확인**에서 멈춘다 (M15 후속). 정리된 제약이 표로 나오고, 한도(최소·최대 …)와 **구간**("area_zone=boundary"처럼 `차원=값1,값2; 차원=값`)을 고칠 수 있다. 쓰지 않을 제약은 체크를 끈다. **[확정]**하면 그 제약으로 다시 제안받고, 고친 값이 형식에 맞지 않으면 이유와 함께 다시 확인을 받는다. 뜻이 다르면 **[다시 적기]**로 사람 검토로 돌아가 의견을 다시 쓴다. **확정한 제약만** 쓰이고 DB에 저장된다.
   - 구간이 붙은 제약은 그 구간에 적용되는 값(전역 값과 구간이 겹치는 구간 조건)만 대조한다. 예: 경계 지역 4km 한도는 중심 지역에만 거는 5km 구간 조건과는 부딪히지 않는다.
6. **종료 판정**: 핵심 지표가 목표(`dimensions.yaml` metrics의 target)에 닿았거나, 이번 회차에 개선이 없거나(승인 없음·최소 효과 미만), 최대 회차(`max_rounds`, 기본 2)면 **결과 보고**로 끝난다. 아니면 **다음 회차**: 배정 에이전트부터 새 규칙으로 다시.
   - 위 줄의 **종료 판정** 선택에서 **Supervisor 에이전트**를 고르면 이 노드가 에이전트가 되어 허용된 다음 단계(다음 회차 · 다시 제안 · 결과 보고) 중에서 고른다. 최대 회차·다시 제안 횟수는 코드가 막는다. 고정 규칙의 판정과 Supervisor의 선택이 결과 줄에 나란히 나온다.
7. **Supervisor 지휘 (M18, 켜고 끄기, 기본 꺼짐)**: 위 줄의 **Supervisor 지휘**를 켜면 분석 에이전트 → 개선 제안 에이전트 → 미리 돌려보기·순위 구간이 **Supervisor 지휘** 노드 하나로 바뀐다. 실행 전에도 켜고 끄면 상위 그래프가 그 모드의 모양으로 바로 다시 그려진다(Supervisor가 있을 때·없을 때 흐름).
   - Supervisor는 분석 에이전트(관점·직접 쓴 질문·구간으로 재분석)·개선 에이전트(대상 발견·초점)·미리 돌려보기(진단 신호 포함)·파라미터 훑기·문서 검색을 도구로 부르며 다음 행동을 스스로 정한다. 그가 부른 에이전트의 진행은 Supervisor 내부 그래프의 도구 노드에 "분석 R1 · …", "개선 B1 · …"로 보인다.
   - 결과는 **판단 보고서**: 추천안(최대 3건), 원인 가설과 확신도, 시도 기록, 사람에게 묻는 것, 끝낸 이유. 추천은 Supervisor가 미리 돌려본 적용 가능한 안만이고, 근거 수치는 인용한 도구 결과에 있어야 한다(코드가 검사, 한 번 돌려보낸 뒤에도 틀리면 "해결 불가").
   - 추천안은 **추천안 차례대로** 노드가 추천 순서대로 사람 검토에 올린다(득실이 갈려도 사람이 본다). 사람 검토 때 화면에 **Supervisor 판단 보고서** 카드: 기대 효과·잃는 것·확신도, 진단 신호(겨냥한 구간 실패율 전→후, 나빠진 지표, 분석이 놓친 구간, 훑기 결과 중 더 나은 점), 사람에게 묻는 것, 접힌 원인 가설·시도 기록·추천하지 않은 안.
   - 모두 반려·의견 → 제약·종료 판정의 "다시 제안"은 Supervisor로 돌아간다(반려 사유와 이전 회차의 판단·결과를 입력으로). 반영 → 재배정·재평가 → 종료 판정은 고정 흐름과 같다.
   - 호출 상한(도구 전체 40, 분석 3, 개선 4)과 실행 예산(추정 $1.5 · 20분, `configs/workflow.yaml`)은 코드가 막는다. 모델은 `llm.yaml` 역할 `supervisor`(gpt-5.4).
7. **저장된 제약 불러오기**(위 줄, 기본 켜짐): 이전 실행에서 확정한 제약을 처음부터 쓴다. 데이터 준비 결과 줄에 "저장된 제약 n개 불러옴"이 나온다. 개선 제안 탭의 **저장된 제약** 펼침에서 끄고 켠다(켜진 제약은 개선 제안 탭의 개선안 요청에도 들어간다).
8. **개선 루프** 칸: 지금 회차, 회차별 배정 성공률 전 → 후, 승인·반려·의견 이력, 쓴 제약, AI 비용·시간. 끝나면 **결과 보고**(종료 이유, 남은 문제, 비용·시간 합)가 붙는다.
9. **문서 검색 (M15-C)**: 개선 제안·의견 정리 에이전트는 `search_knowledge` 도구로 가상 운영 규정(`domains/dispatch/knowledge/`)과 이전 실행의 현장 의견을 찾아 인용한다. 진행 기록에 `search_knowledge`가 보이고, 받지 않은 조항을 인용한 제안은 적용 불가가 된다. 자세한 것은 [docs/knowledge-retrieval.md](knowledge-retrieval.md).

| 요소 | 뜻 |
|---|---|
| 위 줄 (상위 그래프) | 왼쪽→오른쪽 그래프: 데이터 준비 → 배정 에이전트 → 평가 → 규칙 방식 전체 실행 → 분석 에이전트 → 개선 제안 에이전트 → 미리 돌려보기·순위 → 사람 검토 → (의견 정리 에이전트) → 반영 → 재배정·재평가 → 종료 판정 → 결과 보고. 되돌아가는 선이 회차 순환(다음 회차)·다시 제안이다. 카드에 결과 한 줄. 화면보다 넓어서 **실행 중인 노드로 화면이 따라간다** (끌어서 이동, 오른쪽 아래 +/−로 확대) |
| 노드 누르기 | 그 단계의 결과를 맨 아래 왼쪽에, 에이전트면 그 내부 그래프를 가운데 줄에 고정해서 본다 (다시 누르면 실행 중인 것을 따라간다). 점선 테두리가 고른 노드 |
| 가운데 줄 (에이전트 내부) | 고른 에이전트의 하위 그래프. 카드에 지나간 횟수와 마지막 기록, 지금 노드는 강조 |
| 연결선 | 실선 = 바로 연결, 점선 + 라벨 = 조건부 연결(갈래 이름), 노드 아래로 도는 선 = 되돌아감(다시 시도, 결과 전달, 다음 지시서, 다음 회차). 되돌아가는 선은 한 띠에 모여 이름이 겹치므로 **이름은 마우스를 올리거나 방금 지나갔을 때만** 보인다, 노드 위 고리 = 자기 자신으로(다음 제안), **파란 움직이는 선 = 방금 지나간 연결** |
| 카드 색 (왼쪽 띠) | 파랑 = AI, 주황 = 검사, 회색 = 규칙 계산·도구, 초록 = 사람 |
| 맨 아래 | 왼쪽 = 고른(또는 실행 중인) 단계의 결과, 오른쪽 = 진행 기록 (노드 이름 + 한 줄, ✕ 빨강 / ✓ 초록) |

## 9. 리허설 번들로 한 바퀴

1. (선택) 규칙·데이터 탭: 규칙 설정값과 업무 규칙 문서를 훑어본다. 심어둔 문제의 정답은 분석까지 끝난 뒤에 연다.
2. 비교 탭: P1~P4 모두 체크, 데이터 번호 42 → **데이터 생성** → 처리할 건수 **1일차 앞 10건 (시범)**.
3. **L0** 선택 → AI 방식 실행 → 오른쪽 지도·비교표 확인 (규칙 위반 남음).
4. **L3**, **L5**도 실행 → 비교표에서 규칙 위반이 0건이 되는 것을 확인.
5. 결정 과정 탭: 실행 L5, 필터 **다시 시도한 건** → 지시서 선택 → 자동 검사 반려 → 다시 시도 → 확정 흐름.
6. 문제 찾기 탭: **규칙 방식 전체 실행** → **AI 분석 실행** → 찾아낸 비율 3/4, "경계 지역 실패"를 눌러 지도 강조. 정답에 없는 문제(F4)에 맞는 문제/잘못 짚음 확인.
7. 개선 제안 탭: **개선 제안 만들기** → **설정값 제안 모두 미리 돌려보기** → "경계 지역만 3단계 지역 범위 +2km"가 1순위, 요약 줄에 "최소 변경 추천 3 → 4" → **승인** → 반영 이력. ("전역 3단계 지역 범위 대폭 완화"는 참고로 접힌다: 허용 범위 밖)
8. LangGraph agents 탭 (회차 순환, M15-B): 속도 "바로" → **에이전트 준비** → [다음 실행]을 눌러 **사람 검토**(1회차 1순위 +2km)까지 → 메모 칸에 "관할 밖 4km 초과 출동 불가" → **[의견 보내기]** → 의견 정리 에이전트가 `matching.area_extension_km[2] 최대 4` 제약을 만든다 → 개선 제안 에이전트가 규칙 DIST-01을 찾아 인용한 **+1km (제약 반영)** 제안 → **[승인]** → 재배정·재평가 → 종료 판정 "다음 회차" → 2회차(같은 안은 이미 반영돼 본안 없음) → 종료 판정 "개선 없음" → **결과 보고**.

## 10. 자주 막히는 곳

| 증상 | 원인과 해결 |
|---|---|
| "저장된 AI 실행이 없음" (저장된 결과 보기) | 번들에 없는 조건(데이터·레벨·건수)으로 실행했다. 상단 배너의 **다시 볼 수 있는 AI 실행**과 같게 맞춘다 (리허설 번들: P1~P4, 데이터 번호 42, 1일차 앞 10건, L0·L3·L5) |
| "LLM 클라이언트를 만들 수 없음" | API 키가 없다. `.env`에 `ANTHROPIC_API_KEY`를 넣거나, 리허설 번들로 "저장된 결과 보기"를 쓴다 |
| 문제 찾기·개선 제안 탭이 비어 있음 | 앞 탭의 단계가 필요하다: 문제 찾기는 끝난 실행이, 개선 제안은 분석 결과가 있어야 한다 |
| 제안이 모두 승인됨·반려됨이라 다시 못 해 봄 | "저장된 결과 보기"는 서버를 다시 시작하면(`Ctrl+C` 후 재실행) 처음 상태로 돌아간다 |
| 지도에 도로·지명이 안 보임 | 인터넷이 안 되거나 **배경 지도** 체크가 꺼져 있다. 구 경계와 데이터는 그대로 동작한다 |
| 결정 과정에 단계가 없음 | L0~L4 실행을 골랐다. 단계 기록은 과정 기록이 켜진 L5에만 있다 |
| LangGraph agents 탭이 "가짜 AI를 쓸 수 없음" | 가짜 AI는 레포 안의 리허설 정책을 쓴다. 설치된 패키지가 아니라 레포에서 서버를 실행한다 |
| Agent workflow 탭에 설치 안내만 나옴 | LangGraph가 없다: `pip install -e ".[workflow]"` 후 서버를 다시 켠다 |

## 11. 용어표
